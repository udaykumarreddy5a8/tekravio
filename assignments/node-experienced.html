01
Multi-Tenancy Architecture — RLS + Middleware
// 15 marks · Foundation — cannot be patched in later

Multi-tenancy is architectural. You cannot bolt it on afterwards. Every query, every WebSocket event, every job must be scoped to the correct tenant from the very beginning. A single data leak to the wrong tenant is a P1 incident.

PostgreSQL Row-Level Security: Enable RLS on every tenant-scoped table. Policies enforce WHERE tenant_id = current_setting('app.tenant_id'). Application-level filtering is NOT sufficient — DB enforces it.
Tenant resolution middleware: Extracts tenant ID from JWT, sets app.tenant_id session variable on the PostgreSQL connection via SET LOCAL before every query. Uses AsyncLocalStorage to propagate tenant context through async call chains.
Tenant provisioning API: Create tenant, assign subdomain, provision dedicated S3 prefix, set per-tenant rate limit config. All in one atomic transaction.
Cross-tenant access test: Write a test where Tenant A's JWT attempts to access Tenant B's data via direct ID. Assert 404 (not 403 — never confirm the resource exists).
Connection pooling with tenant context: PgBouncer or native pooling configured correctly so tenant context doesn't bleed between pooled connections. Prove it with a test.
tenantMiddleware.jsJS
const tenantMiddleware = async (req, res, next) => {
  const { tenantId } = jwt.verify(req.headers.authorization?.split(' ')[1], SECRET);
  // Store in AsyncLocalStorage — survives async hops
  tenantContext.run({ tenantId }, async () => {
    const client = await pool.connect();
    try {
      // Set RLS context on this connection
      await client.query(`SET LOCAL app.tenant_id = $1`, [tenantId]);
      req.db = client;
      await next();
    } finally { client.release(); }
  });
};
02
BullMQ Job Queues — Background Processing at Scale
// 20 marks · Async reliability

Synchronous email sending, file processing, and report generation will kill your API response times. Every one of these goes into a queue. Your API acknowledges receipt and returns immediately. A separate worker process handles the work.

Three queues: email-queue (priority), file-processing-queue (concurrency: 5), report-queue (cron + on-demand). Each queue has its own worker with correct concurrency settings.
Job priority: Password reset emails are priority 1. Marketing emails are priority 10. BullMQ processes high-priority jobs first even when lower-priority jobs were added earlier.
Exponential backoff retry: Failed jobs retry at 1s, 2s, 4s, 8s intervals. After 5 failures, move to DLQ. Log failure reason and full stack trace per attempt.
Job progress streaming: Long-running file processing jobs emit progress events (0–100%). Frontend receives real-time progress via WebSocket (same job ID as subscription key).
Cron jobs with tenant context: Scheduled reports run per-tenant on their configured schedule. Job payload includes tenantId. Worker sets RLS context before every DB query.
Bull Board dashboard: Mount Bull Board at /admin/queues (auth protected). Show queue depth, failed jobs, job details. We will check this during review.
03
Webhook Delivery System — Reliable Outbound Events
// 20 marks · Enterprise integration layer

Enterprise clients integrate your platform with their own systems via webhooks. When a job completes, a file uploads, or a report is ready — their endpoint gets called. This must be reliable, verifiable, and auditable.

HMAC-SHA256 signature: Every webhook includes X-Tekravio-Signature: sha256=... header. Payload is the raw JSON body. Secret is per-tenant, rotatable. Client verifies signature before processing.
Reliable delivery via BullMQ: Each webhook attempt is a job. Exponential backoff: 1s, 5s, 30s, 2min, 10min. After 5 failures, mark as FAILED and stop retrying. Never retry a 4xx response.
Webhook delivery log: Every attempt logged: timestamp, HTTP status, response body (truncated to 1KB), latency, attempt number. Exposed via GET /webhooks/deliveries per tenant.
Circuit breaker per endpoint: If an endpoint returns 5xx on 5 consecutive attempts, pause all webhooks to that endpoint for 10 minutes. Notify tenant via email. Auto-resume after pause.
Idempotency: Each webhook event has a unique X-Tekravio-Event-ID header. Client can use this to deduplicate if they receive the same event twice during a retry.
04
Real-Time with Socket.io — Tenant-Scoped Rooms
// 15 marks · Real-time layer

Tenant dashboards need live updates — job progress, new records, notification counts. Socket.io rooms keep tenants isolated. The Redis adapter allows horizontal scaling so two API instances can serve the same tenant.

Authentication middleware: Socket.io connection authenticated via JWT in handshake. Client automatically joins their tenant room on connect. Unauthenticated connections rejected.
Tenant room isolation: Events emitted to tenant:{tenantId} room only. A connected client from Tenant A must never receive events for Tenant B under any circumstances.
Redis adapter for scaling: Socket.io configured with @socket.io/redis-adapter. Two running API instances can both emit to the same tenant room. Demonstrate with a test using two separate socket clients.
Job progress events: When a BullMQ job emits progress (0–100%), the worker publishes to Redis. The API instance picks it up via Redis pub/sub and emits to the correct tenant room.
Connection cleanup: On disconnect, remove client from room. Track connected user count per tenant. Expose via GET /admin/connections.
05
Rate Limiting, Audit Logging & Security
// 20 marks · Production security

Per-tenant rate limits. Every mutating action logged immutably. API keys with scoped permissions. This is what separates a demo from a system you'd trust with enterprise data.

Per-tenant rate limiting: Different tenants have different limits (Free: 100/min, Pro: 1000/min, Enterprise: custom). Limits stored in Redis per tenant. 429 response includes X-RateLimit-Limit, X-RateLimit-Remaining, Retry-After.
Scoped API keys: Tenants generate API keys with specific scopes (read:reports, write:jobs, admin:webhooks). Key hashed with bcrypt before storage — never stored in plaintext. Revocation invalidates immediately via Redis cache.
Immutable audit log: Every CREATE/UPDATE/DELETE action appended to audit_log table with: actor (userId or apiKeyId), tenant, resource type, resource ID, action, old value (JSON), new value (JSON), IP, timestamp. No UPDATE or DELETE on this table — append only.
SQL injection prevention: Zero string concatenation in queries. Parameterised queries everywhere. Write a test that attempts SQL injection via every user-controlled input field and asserts it is handled safely.
Sensitive data in logs: Write a middleware that strips passwords, API keys, credit card numbers, and email addresses from all log output. Test it by asserting your logs contain no PII after processing a user registration request.
06
Test Suite — Integration & Load
// 10 marks · Quality discipline

Multi-tenancy bugs are the worst kind — they're silent and catastrophic. Your tests must prove tenant isolation works under load, not just in happy-path scenarios.

Tenant isolation test: 3 tenants, 100 records each, 30 concurrent requests mixing all tenants. Assert zero cross-tenant data leaks. Run with TestContainers PostgreSQL.
Webhook delivery test: Mock endpoint returns 500 for first 4 attempts, 200 on 5th. Assert exactly 5 attempts made with correct backoff timing and final DELIVERED status.
BullMQ job test: Submit 50 jobs simultaneously. Assert all complete. Assert priority queue processes priority-1 jobs before priority-10 jobs.
Rate limit test: Submit 110 requests as same tenant (limit: 100/min). Assert first 100 succeed, next 10 return 429 with correct headers.
Socket.io isolation test: Two clients from different tenants connected. Emit event to Tenant A. Assert Tenant B client receives nothing.

// Mindset

Answer these in your README

We read these before we run your code. At experienced level, system design thinking matters as much as implementation.

// Q1
Your BullMQ worker crashes mid-job after partially processing a file upload (50% complete). When it restarts, it picks up the same job. How do you prevent partial processing from causing data corruption or duplicate work?
// Q2
A tenant with 10,000 WebSocket connections suddenly disconnects (their datacenter goes down). All 10,000 disconnect events hit your API simultaneously. What happens to your Redis adapter, your event loop, and your other tenants's real-time features?
// Q3
Your webhook delivery queue has 500,000 pending jobs — a large tenant triggered a bulk event. New jobs from other tenants are stuck behind them. How do you design the queue architecture so one tenant's volume can't starve others?
// Q4
A junior developer suggests: "Instead of RLS, let's just add WHERE tenant_id = :tenantId to every query. It's simpler." Explain exactly how this can fail — give a specific code example where a developer would forget it and what data leaks as a result.
// Q5
Your Redis cluster goes down. Map out exactly which features of your system fail immediately, which degrade gracefully, and which continue working normally. Include: job queues, rate limiting, WebSocket scaling, API key revocation, webhook circuit breakers.
