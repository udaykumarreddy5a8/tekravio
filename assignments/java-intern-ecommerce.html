// The Problem
ShopNest has two roles: ADMIN (manages products, inventory, coupons) and CUSTOMER (browses, carts, orders). A product like "Running Shoes" has variants: Size 8 Blue (stock: 5), Size 8 Red (stock: 3), Size 9 Blue (stock: 0). A customer adds a variant to their cart, applies a coupon for a discount, and places an order.

Key challenge — inventory: when an order is placed, stock for each ordered variant must be decremented atomically. If any variant is out of stock, the entire order must fail. When an order is cancelled, stock must be restored. This must work correctly even when two customers order the last item simultaneously.

01
Product Catalogue & Inventory
// 22 marks
▼

Products with variants, each variant tracked separately in inventory.

StockService.java — atomic decrementService
// Called during order placement for each variant in cart
@Transactional
public void decrementStock(UUID variantId, int quantity) {
    int updated = variantRepository.decrementStock(variantId, quantity);
    if (updated == 0) {
        throw new InsufficientStockException(
            "Not enough stock for variant: " + variantId);
    }
}

@Modifying
@Query("UPDATE ProductVariant v SET v.stockQuantity = v.stockQuantity - :qty " +

int decrementStock(@Param("id") UUID id, @Param("qty") int qty);
Product entity: Fields: name, description, category (CLOTHING, FOOTWEAR, ELECTRONICS, HOME, BEAUTY, OTHER), brand, basePrice (BigDecimal), imageUrls (stored as comma-separated or JSON array), isActive, createdAt. A product has many ProductVariants.
ProductVariant entity: Fields: product, variantName (e.g., 'Size 8 / Blue'), sku (unique), additionalPrice (BigDecimal, added to basePrice), stockQuantity (int, ≥ 0), weight (for shipping). The selling price = product.basePrice + variant.additionalPrice. Never allow stockQuantity to go below 0.
Inventory management: PUT /api/admin/variants/{id}/stock — ADMIN only. Body: {operation: 'ADD'|'REMOVE'|'SET', quantity}. ADD increases stock. REMOVE decreases stock (throw InsufficientStockException if result < 0). SET directly sets to value (≥ 0 only). Every stock change creates a StockAuditLog entry: variantId, operation, quantityChange, reason, changedBy, changedAt.
Product APIs: POST /api/admin/products — create with variants. GET /api/products?category=FOOTWEAR&brand=Nike&minPrice=500&maxPrice=5000&inStock=true&page=0&size=20 — paginated search. GET /api/products/{id} — product with all variants, stock status (IN_STOCK if qty > 0, LOW_STOCK if qty 1–5, OUT_OF_STOCK if qty = 0).
02
Shopping Cart
// 20 marks
▼

Cart management with quantity controls and real-time price calculation.

Cart design: One cart per user (persisted in DB, not session). Cart has many CartItems; each CartItem has variant, quantity, addedAt. Cart is always up-to-date — it shows current prices (not the price when item was added). Add a priceChangedWarning flag when the current variant price differs from when the item was added.
Cart operations: POST /api/cart/items — add item (variantId + quantity). Validate: variant exists, is active, and quantity does not exceed available stock. If item already in cart, increment quantity (up to stock limit). PUT /api/cart/items/{id} — update quantity. DELETE /api/cart/items/{id} — remove item. DELETE /api/cart — clear entire cart.
Cart summary: GET /api/cart — return items with: variantId, variantName, productName, imageUrl, unitPrice, quantity, lineTotal (unit × qty), and cart-level: subtotal, appliedCoupon (if any), discountAmount, finalTotal, itemCount. Warn if any item's stock has dropped below the cart quantity since it was added.
Stock reservation warning: If a customer adds 3 units of a variant with 5 in stock, and then another customer buys 4 (leaving only 1), the first customer's cart shows quantity=3 but only 1 is available. Add a availableStock field per cart item so the frontend can warn the customer before checkout.
03
Coupon & Discount Engine
// 18 marks
▼

Coupons can be percentage or flat discounts with usage limits and expiry.

Coupon entity: Fields: code (String, unique, uppercase), type (PERCENTAGE, FLAT_AMOUNT), value (BigDecimal — 20 for 20% off, or 200 for ₹200 off), minimumOrderAmount (BigDecimal, optional), maximumDiscountAmount (BigDecimal, optional cap for % coupons), totalUsageLimit (int), usedCount (int, starts 0), validFrom (LocalDateTime), validUntil (LocalDateTime), isActive.
Apply coupon to cart: POST /api/cart/coupon — body: {couponCode}. Validate: coupon exists and isActive, not expired, minimum order amount met, usedCount < totalUsageLimit. For PERCENTAGE: discount = subtotal * value/100 (capped by maximumDiscountAmount). For FLAT: discount = min(value, subtotal). Return updated cart totals. Only one coupon per cart.
Coupon CRUD (admin): POST /api/admin/coupons, PUT /api/admin/coupons/{id}, DELETE /api/admin/coupons/{id}. Cannot delete a coupon that has usedCount > 0 (deactivate instead). Return usage stats: usedCount, remainingUses, revenue discounted.
Coupon validation edge cases: Test these: (a) expired coupon → COUPON_EXPIRED, (b) minimum order not met → MINIMUM_ORDER_NOT_MET with the required amount in error, (c) usage limit reached → COUPON_EXHAUSTED, (d) applying a coupon when one is already applied → replace old coupon, (e) removing a coupon: DELETE /api/cart/coupon.
// Note

Increment usedCount at order placement, NOT at coupon application. A user can apply and remove coupons from their cart many times. Only when they actually place an order does the coupon count as used.

04
Order Management & Inventory Sync
// 22 marks
▼

Order placement must atomically deduct stock. Cancellation must restore it.

OrderService.java — atomic placementService
@Transactional
public OrderResponse placeOrder(PlaceOrderRequest req) {
    Cart cart = cartService.getCartForCurrentUser();
    if (cart.getItems().isEmpty()) throw new EmptyCartException();

    // Step 1: validate + decrement stock atomically for ALL items
    cart.getItems().forEach(item -> {
        stockService.decrementStock(item.getVariant().getId(), item.getQuantity());
        // throws InsufficientStockException if stock < qty
        // @Transactional ensures all decrements roll back on any failure
    });

    Order order = buildOrder(cart, req.deliveryAddress());
    orderRepository.save(order);
    cartService.clearCart();
    return orderMapper.toResponse(order);
}
Order placement: POST /api/orders — places order from current cart. In a single @Transactional method: (1) snapshot cart items and prices, (2) validate all variants still have sufficient stock, (3) decrement stock for each variant using the atomic query from Module 1, (4) if any decrement returns 0 (insufficient stock), throw InsufficientStockException and roll back all decrements, (5) if coupon applied, increment coupon usedCount and validate it's still valid, (6) create Order + OrderItems, (7) clear cart.
Order entity: Fields: customer, status (PENDING, CONFIRMED, SHIPPED, DELIVERED, CANCELLED), subtotal, discountAmount, totalAmount, couponCode, deliveryAddress (embedded or separate entity), createdAt, updatedAt. OrderItem: order, variant, variantName (snapshot at order time), unitPrice (snapshot), quantity, lineTotal.
Order status transitions: Valid: PENDING→CONFIRMED, CONFIRMED→SHIPPED, SHIPPED→DELIVERED, PENDING→CANCELLED, CONFIRMED→CANCELLED. Invalid transitions throw InvalidOrderStatusException. PUT /api/admin/orders/{id}/status — ADMIN updates status. PUT /api/orders/{id}/cancel — CUSTOMER can cancel only own PENDING orders.
Stock restoration on cancel: When an order is CANCELLED: restore stock for each OrderItem variant. Use the same atomic update pattern. If the variant was deleted (rare), log a warning but don't fail the cancellation.
Order history: GET /api/orders?status=DELIVERED&page=0&size=10 — customer's own orders with items. GET /api/admin/orders?customerId=&status=&from=&to= — admin view with pagination.

// 02 · Design Questions
Answer in README.md
Q1
Two customers simultaneously add the last item (stock: 1) to their carts and both click 'Place Order' at the same time. Walk through what happens in your system. Does one of them get an error? Which one? How does the database ensure only one succeeds?
Q2
You snapshot the variant name and price at order time into the OrderItem. Why? What would go wrong if you just stored a foreign key to ProductVariant and queried it live when showing order history?
Q3
A DELIVERED order cannot be cancelled. But a CONFIRMED order can. What real business rule is this simulating? What happens to inventory when a CONFIRMED order is cancelled vs when it was never confirmed?
Q4
The product search API supports filtering by category, brand, price range, and in-stock status. With 1 million products in the DB, which indexes do you need? Write the specific column combinations to index.
