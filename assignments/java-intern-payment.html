// The Problem
PayFlow is a simulated payment backend. Two actor types: USER (customer with a wallet) and MERCHANT (business receiving payments). A user tops up their wallet, initiates a payment to a merchant for a specific order, and can request a refund within 7 days of a successful payment. Merchants can check payment status for their orders.

Key challenge — idempotency: a caller sends an idempotency key (X-Idempotency-Key header) with each payment request. If the same key is submitted twice, return the original payment response — do not create a duplicate payment. This is table stakes for any payment API.
// 01 · Modules
Five Modules — 100 Marks

Build in order. Module 1 (wallet) must be solid before building payments on top of it.

01
Wallet Management
// 20 marks
▼

Every user has one wallet. Wallet operations must be atomic and consistent.

Wallet entity: Fields: userId (one-to-one with User), balance (BigDecimal, cannot go below 0), currency (default INR), status (ACTIVE, SUSPENDED), createdAt, updatedAt. Auto-create a wallet when a user registers.
Top-up: POST /api/wallet/topup — body: {amount, paymentMethod: 'UPI'|'CARD'|'NETBANKING', transactionRef}. Validate amount > 0 and ≤ 100,000. Simulate payment gateway (just mark as success, no real gateway). Atomically add to wallet balance and create a WalletTransaction record of type CREDIT.
Deduct (internal use): Create an internal WalletService.deduct(userId, amount, referenceId) method. It must: (a) check wallet is ACTIVE, (b) check balance ≥ amount, else throw InsufficientBalanceException, (c) subtract balance, (d) create WalletTransaction of type DEBIT atomically. This is called by the payment service, not exposed directly via HTTP.
Wallet statement: GET /api/wallet/statement?from=&to=&page=&size= — paginated list of WalletTransactions: type, amount, referenceId (payment ID or topup ID), description, createdAt, runningBalance. Running balance must be calculated (not stored) by processing transactions in time order.
02
Payment Processing & Idempotency
// 25 marks
▼

The core of the system. Every payment has a lifecycle: INITIATED → PROCESSING → SUCCESS or FAILED.

PaymentService.java — idempotency checkService
@Transactional
public PaymentResponse initiatePayment(String idempotencyKey, PaymentRequest req) {
    // idempotency: return existing if key already used
    return paymentRepository
        .findByIdempotencyKeyAndUserId(idempotencyKey, currentUser().getId())
        .map(paymentMapper::toResponse)           // return existing
        .orElseGet(() -> processNewPayment(idempotencyKey, req));
}

private PaymentResponse processNewPayment(String key, PaymentRequest req) {
    Payment payment = createPaymentRecord(key, req);   // status: INITIATED
    payment.setStatus(PaymentStatus.PROCESSING);
    try {
        walletService.deduct(currentUser().getId(), req.amount(), payment.getId());
        payment.setStatus(PaymentStatus.SUCCESS);
    } catch (InsufficientBalanceException e) {
        payment.setStatus(PaymentStatus.FAILED);
        payment.setFailureReason("Insufficient wallet balance");
    }
    return paymentMapper.toResponse(paymentRepository.save(payment));
}
Payment entity: Fields: id (UUID), idempotencyKey (String, unique per user), userId, merchantId, orderId (String, provided by merchant), amount, currency, status (INITIATED, PROCESSING, SUCCESS, FAILED), paymentMethod, failureReason, initiatedAt, processedAt. Index on (userId, idempotencyKey) — unique constraint.
Idempotency handling: In POST /api/payments, read the X-Idempotency-Key header. If a payment with this key already exists for this user: return the existing payment (status 200, same response body). If not, create a new payment. Implement this check at the start of the service method inside a @Transactional block to prevent race conditions.
Payment flow: When a payment is created: (1) set status to INITIATED, (2) set to PROCESSING, (3) call walletService.deduct(), (4) on success set to SUCCESS and notify merchant (just log for now), (5) on InsufficientBalanceException set to FAILED with reason. All state changes must be persisted. Steps 1–5 in one @Transactional method.
Status check: GET /api/payments/{id} — USER can check own payments. MERCHANT can check payments where merchantId matches. Return full payment details including wallet transaction reference if SUCCESS.
Payment history: GET /api/payments?status=SUCCESS&from=2026-01-01&to=2026-06-30&page=0&size=20 — user's payment history with filters.
03
Refund Management
// 22 marks
▼

Refunds are a second payment in reverse. They have their own rules and lifecycle.

Refund entity: Fields: id, originalPaymentId, amount (BigDecimal, ≤ original payment amount), type (FULL, PARTIAL), status (PENDING, APPROVED, PROCESSED, REJECTED), requestedAt, processedAt, reason, processedBy (admin user ID).
Refund eligibility rules: A refund can only be requested if: (a) original payment status is SUCCESS, (b) payment was made within the last 7 days, (c) no existing PENDING or APPROVED refund for this payment. For partial refunds: amount must be > 0 and ≤ (original amount - already refunded amount). Throw typed exceptions for each violation.
Request refund: POST /api/refunds — body: {paymentId, amount, reason}. If amount equals remaining refundable amount, set type FULL, else PARTIAL. Set status PENDING. Users request their own refunds only.
Process refund (admin): PUT /api/refunds/{id}/approve and PUT /api/refunds/{id}/reject — ADMIN role only. On approve: credit the wallet via walletService.credit(), set status PROCESSED, update original payment's refunded amount. On reject: set status REJECTED with rejection reason.
Refund status: GET /api/refunds/{id} — user can check status of their own refund. Return original payment details, refund amount, status, and if processed, the wallet credit reference.
// Note

Track refundedAmount on the Payment entity. It starts at 0 and increments with each processed refund. This prevents over-refunding without querying all refunds each time.

04
Merchant & Settlement
// 18 marks
▼

Merchants register, receive payments, and view settlement summaries.

Merchant entity: Fields: businessName, email, phone, status (ACTIVE, SUSPENDED), settlementAccount (bank account number), createdAt. Merchant is a separate user role from USER.
Payment verification: GET /api/merchant/payments/verify?orderId={orderId} — merchant checks if a payment for a specific orderId is SUCCESS. Returns payment status, amount, paymentMethod, processedAt. A merchant can only query payments where merchantId matches their account.
Settlement summary: GET /api/merchant/settlements?month=2026-06 — for the given month: totalTransactions, totalAmount, totalRefunds, totalRefundedAmount, netSettlement (total - refunded). Show day-by-day breakdown as a list.
Suspend merchant: PUT /api/admin/merchants/{id}/suspend — ADMIN only. When suspended, any new payment to this merchant returns MerchantSuspendedException (status 422).
// Note

'Settlement' here is reporting only. You do not need to simulate actual bank transfers. Just report the net amount the merchant should receive.

05
Testing & API Quality
// 15 marks
▼

Payment systems demand high test coverage. Every edge case must be tested.

Unit tests: Test PaymentService: (a) new payment with valid balance — status SUCCESS, (b) payment with insufficient balance — status FAILED, (c) duplicate idempotency key returns existing payment, (d) refund requested after 7 days throws exception, (e) partial refund cannot exceed remaining refundable amount, (f) payment to suspended merchant throws exception. 6 tests.
Wallet balance assertion: In your payment success test: assert wallet balance before = X, after payment of Y = X-Y, after refund of Z = X-Y+Z. Use BigDecimal.compareTo(), never .equals() for comparing amounts.
Global error responses: All errors: {status, error, message, timestamp}. Specific: InsufficientBalanceException → 422 with "Insufficient balance". DuplicateIdempotencyKeyException → 200 (return the original). RefundNotEligibleException → 422. MerchantSuspendedException → 422.
API documentation: Swagger at /swagger-ui.html. Document the X-Idempotency-Key header requirement on the payment endpoint. Show example request/response for payment success AND payment failure in the Swagger examples.
// 02 · Design Questions
Answer in README.md

These are the questions a payment team lead would ask in a code review.

Q1
Two simultaneous requests arrive with the same idempotency key for the same user. Your database has a unique constraint on (userId, idempotencyKey). What happens at the database level if both requests pass the application-level idempotency check simultaneously? How do you handle the resulting database constraint violation exception?
Q2
A payment deducts from the wallet successfully (step 3), but then the server crashes before setting status to SUCCESS (step 4). When the server restarts, the payment is in PROCESSING state but the wallet is already deducted. How should the system recover? Write a pseudo-code recovery strategy.
Q3
A user requests a full refund of ₹1,000. The approve endpoint calls walletService.credit() which succeeds, but then the database write to set refund status to PROCESSED fails. The user's wallet has ₹1,000 but the refund still shows PENDING. How do you prevent this? What @Transactional boundary is needed?
Q4
Your payment history API supports filtering by status, date range, and pagination. With 100,000 payments in the database, which database indexes should you create? Write the exact CREATE INDEX statements for your payments table.
// Bonus Tasks — 20 Additional Marks
+8 marks — Payment expiry: A payment in PROCESSING status for more than 10 minutes should automatically be marked FAILED and the wallet deduction reversed (if any). Implement a scheduled job @Scheduled(fixedDelay = 60000) that handles stuck payments.
+7 marks — Split payment: Allow a payment to be funded partially from wallet and partially from another method. E.g., order worth ₹1,500: pay ₹800 from wallet + ₹700 from UPI. Store both funding sources on the payment. Wallet deduction is real; UPI is simulated.
+5 marks — Webhook simulation: When a payment status changes to SUCCESS or FAILED, make an HTTP POST call to the merchant's registered webhookUrl (store this on the merchant entity). Use RestTemplate or WebClient. Handle failures gracefully — if the webhook call fails, log and continue; do not fail the payment.
