// The Problem
PayFlow frontend has two distinct UIs: customer and merchant. Both share auth but have completely different layouts after login. The most interesting challenge is the payment status polling — it must start on submit, update the UI in real time, and stop cleanly on navigation or terminal state. Use useInfiniteQuery for the wallet statement infinite scroll and refetchInterval for status polling.
// 01 · Modules
Five Modules — 100 Marks

This is a frontend assignment. Every module requires working UI components, not just API calls. Show state, loading, and error states for every async operation.

01
Wallet Dashboard & Top-Up
// 20 marks
▼

The customer's wallet overview and top-up flow.

Wallet card: Prominent card showing current balance (large, animated count-up on load), account status (ACTIVE badge), and three quick-action buttons: Top Up, Pay, History.
Top-up modal: A three-step modal: (1) Enter amount (validation: 1–100,000, number-only input with a soft keyboard hint), (2) Choose payment method (card-style selectors for UPI / Card / Net Banking), (3) Confirmation screen showing amount + method + 'Confirm & Add' button. A back button on steps 2 and 3 goes back without losing selections.
Balance animation: After a successful top-up, animate the balance from old value to new value over 1 second. Use a useCountUp hook.
Wallet statement: Paginated table of wallet transactions: type icon (credit green arrow / debit red arrow), description, amount, date, reference ID. Infinite scroll (not page buttons). Implemented with TanStack Query's useInfiniteQuery.
02
Payment / Checkout Flow
// 25 marks
▼

A multi-step checkout that handles the full payment lifecycle.

Checkout steps: Three steps managed by a stepper component: (1) Order summary (merchant name, order ID, amount), (2) Payment method selection (Wallet / UPI / Card), (3) Confirmation. Stepper shows progress. Back button works on all steps and does not lose selections.
Wallet balance check: On step 2, if the user selects Wallet and their balance is less than the payment amount, show an inline warning: 'Insufficient balance. You need ₹X more.' with a shortcut 'Top Up Now' link that opens the top-up modal in a portal, then returns to checkout.
Idempotency key: Generate a UUID v4 as the idempotency key when the checkout flow begins. Store it in component state. Pass it as X-Idempotency-Key header on the payment API call. If the user submits twice (e.g., double-click), the same key is used, and the backend returns the existing payment.
Payment result: After submission: navigate to a payment status page with the payment ID in the URL. This page polls GET /api/payments/{id} every 3 seconds using TanStack Query's refetchInterval. Show a spinner while PROCESSING, a green success screen with confetti on SUCCESS, a red failure screen with retry option on FAILED. Stop polling when a terminal state is reached.
03
Transaction History & Refunds
// 20 marks
▼

Customer's payment history with refund request flow.

Payment history: Table of past payments: merchant name, order ID, date, amount, status badge (SUCCESS green, FAILED red, PENDING yellow). Filter by status and date range. Click a row to open a slide-in detail panel.
Payment detail panel: Shows: all payment fields, merchant name, wallet balance at time of payment (if available), and — if payment is SUCCESS and within 7 days — a 'Request Refund' button.
Refund form: A bottom sheet (on mobile) or modal (on desktop). Input: amount (pre-filled with payment amount, editable for partial refund), reason text. Validation: amount must be > 0 and ≤ refundable amount. On submit, show success and update the payment row's status badge to show 'Refund Pending'.
Refund status: A separate 'My Refunds' section showing refund requests with their statuses. PENDING shown with a clock icon, PROCESSED with a green check, REJECTED with an explanation.
04
Merchant Dashboard
// 18 marks
▼

The merchant-facing interface for viewing payments and settlements.

Payment verification: A prominent 'Verify Payment' widget: input field for Order ID, a search button, and a result display. If payment is SUCCESS: show a green confirmation with amount and timestamp. If PENDING/FAILED: show appropriate status. Keyboard shortcut: Enter triggers search.
Settlement summary: A summary card for the current month: total transactions, gross amount, total refunded, net settlement amount (highlighted in green). Below it, a day-by-day bar chart of daily transaction volume.
Payments table: Paginated list of all payments to this merchant. Columns: order ID, customer ID (masked), amount, method, status, date. Searchable by order ID. Exportable to CSV.
Suspended state: If the merchant's account is SUSPENDED, the entire dashboard shows a fullscreen overlay: 'Account Suspended. Contact support.' No actions are allowed. The overlay cannot be dismissed.
05
Auth, Error Handling & UX Polish
// 17 marks
▼

The reliability layer: errors, edge cases, and UX details.

Auth & role routing: After login, check the user's role (CUSTOMER / MERCHANT). Route to the wallet dashboard for CUSTOMER or the merchant dashboard for MERCHANT. A customer navigating to a merchant URL sees a 403 page and vice versa.
API error handling: All API errors must be caught. For 4xx: show the error message from the API response body inline near the relevant action (not a toast for validation errors). For 5xx or network errors: show a toast with 'Something went wrong. Please try again.'
Payment polling edge case: The payment status polling runs every 3 seconds. What if the user navigates away while polling? The polling must stop when the component unmounts. Implement with TanStack Query's enabled flag based on status.
Form double-submission prevention: Every form button shows a loading state on submit and is disabled until the API responds. Implement a useSubmit hook that wraps any async function, manages loading state, and prevents concurrent calls.
// 02 · Design Questions
Answer in README.md

These come up in every React frontend interview.

Q1
The checkout flow is a 3-step form. The user is on step 3 and clicks Back. What happens to the data they entered on steps 1 and 2? Where do you store intermediate form state? React state, React Hook Form, or Zustand?
Q2
The payment status page polls every 3 seconds. The page has been open for 10 minutes with the payment stuck in PROCESSING (backend is down). How do you handle this? At what point do you stop polling and show an error?
Q3
You generate the idempotency key when the checkout flow begins. What if the user opens two checkout tabs for the same order at the same time? They would have different idempotency keys. Is this a frontend problem or a backend problem?
Q4
The refund amount input is pre-filled with the full payment amount. The user types '500' to request a partial refund of ₹500. How do you validate that ₹500 is ≤ the remaining refundable amount (original amount - already refunded)? Where does this business logic live?
// Bonus — 20 Additional Marks
+8 marks — Optimistic wallet update: When a payment is submitted, optimistically deduct the amount from the displayed wallet balance before the API responds. If the payment fails, restore the balance. Implement with TanStack Query's optimistic update pattern.
+7 marks — Receipt download: After a successful payment, provide a 'Download Receipt' button that generates a PDF receipt client-side using @react-pdf/renderer. Include: payment ID, merchant name, amount, date, and a simple logo.
+5 marks — Currency formatting: Support both INR and USD display (even though the backend only uses INR). A currency toggle in the header shows amounts converted using a hardcoded rate. All amounts update when the currency changes.
