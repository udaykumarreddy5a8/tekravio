// The Problem
FinSmart FastAPI uses Python's built-in decimal.Decimal with ROUND_HALF_UP for all monetary arithmetic. SQLAlchemy DECIMAL(19,4) for all monetary DB columns. All balance modifications use SQLAlchemy's async with db.begin(): transaction context manager. The recurring transactions job runs via APScheduler integrated into FastAPI's lifespan events.

01
Account & Transaction Management
// 22 marks
▼

Typed account and transaction service with atomic balance update.

SQLAlchemy Decimal: balance: Mapped[Decimal] = mapped_column(DECIMAL(19, 4), default=Decimal('0')). All arithmetic: from decimal import Decimal, ROUND_HALF_UP. Use: result = Decimal('100.10') + Decimal('200.20').
Async transaction: async def create_transaction(dto: TransactionCreate, db: AsyncSession, user: User) -> TransactionResponse. Use SQLAlchemy's async with db.begin(): to wrap the balance update + transaction insert. If any statement fails, the context manager rolls back automatically.
Account ownership dependency: async def get_user_account(account_id: UUID, db: AsyncSession, user: User = Depends(get_current_user)) -> Account. Raises HTTPException(404) if not found, HTTPException(403) if not owned by user.
Balance recalculation: Use SQLAlchemy aggregate: income = await db.scalar(select(func.sum(Transaction.amount)).where(Transaction.account_id == aid, Transaction.type == 'INCOME')) or Decimal('0'). Return income - expenses.

BudgetStatus enum: Python enum.StrEnum: class BudgetStatus(StrEnum): ON_TRACK = 'ON_TRACK'; WARNING = 'WARNING'; OVER_BUDGET = 'OVER_BUDGET'. Compute: pct = (spent / limit * 100).quantize(Decimal('0.01'), ROUND_HALF_UP).
Month parameter validation: Pydantic: month: str = Query(pattern=r'^\d{4}-\d{2}$'). In the route: parse to date with datetime.strptime(month + '-01', '%Y-%m-%d').date().
03
Savings Goals & Deposits
// 20 marks
▼

Goal deposits with atomic account deduction and projected date calculation.

Goal deposit: async with db.begin(): deduct account balance; add to goal current_amount; create GoalDeposit; if goal.current_amount >= goal.target_amount: goal.status = GoalStatus.ACHIEVED. All in one SQLAlchemy transaction context.
Projected date: Use Python's relativedelta or timedelta math. Average daily deposit: daily_rate = recent_total / Decimal('30'). Days needed: math.ceil(float(remaining / daily_rate)). Return date.today() + timedelta(days=days_needed).
Pydantic validators: Use Pydantic v2's @field_validator: @field_validator('target_date') @classmethod def target_must_be_future(cls, v): if v <= date.today(): raise ValueError('Target date must be in the future'); return v.
Goal response: Use Pydantic computed_field: @computed_field @property def progress_percentage(self) -> Decimal: return (self.current_amount / self.target_amount * 100).quantize(Decimal('0.1'), ROUND_HALF_UP).

// 02 · Design Questions
Answer in README.md

Python/FastAPI-specific patterns.

Q1
Python's decimal.Decimal arithmetic is exact. But when you write Decimal('100.10') + Decimal('200.20'), what do you get? Is it exactly 300.30 or 300.3? What is the difference, and when does it matter for financial display?
Q2
SQLAlchemy's async with db.begin(): creates a transaction that auto-commits on exit and auto-rollbacks on exception. But what if you need to do something AFTER the transaction commits (e.g., send a notification)? How do you structure this correctly?
Q3
Your 6-month trend can be computed either with a loop of 6 async queries or with one SQL query using date_trunc. The one-query approach sends one round trip to the database. The loop approach sends 6 round trips but each query is simpler. Which do you implement and why?
Q4
APScheduler runs a recurring transaction job. The FastAPI app is deployed with 3 workers (Gunicorn with 3 uvicorn workers). The scheduler runs in each worker. The cron job will run 3 times. How do you prevent this?
