// The Problem
ShopNest Node.js uses Prisma's updateMany with WHERE stock >= qty as the atomic safety net for inventory. The WHERE clause prevents overselling without locks. All Prisma monetary fields use the Decimal type. Coupon discounts computed with decimal.js. Order items snapshot the variant name and price at placement time so historical orders are never affected by product edits.
// 01 · Modules
Five Modules — 100 Marks

TypeScript strict mode throughout. No any. Every Zod schema exported from a schemas/ folder. Every Prisma query wrapped in a typed service class.

01
Product Catalogue & Inventory
// 22 marks
▼

Typed product CRUD with atomic stock management.

Prisma schema: Product with variants ProductVariant[]. ProductVariant with stockQuantity Int @default(0) and a check constraint: @@check(fields: [stockQuantity], name: 'stock_non_negative', expression: 'stockQuantity >= 0').
Atomic stock decrement: prisma.productVariant.updateMany({ where: { id: variantId, stockQuantity: { gte: quantity } }, data: { stockQuantity: { decrement: quantity } } }). Check the count result: if 0 rows updated, throw OutOfStockError. This WHERE clause is the atomic safety net.
Stock audit log: Every stock change creates a StockAuditLog via Prisma middleware (Client Extension): intercept all productVariant.update calls that change stockQuantity and automatically create the audit entry.
Product search: Prisma findMany with Prisma.ProductWhereInput built conditionally from Zod-validated query params. Include _count: { select: { variants: true } }. Filter by inStock using: variants: { some: { stockQuantity: { gt: 0 } } }.
02
Cart & Coupon Engine
// 22 marks
▼

Database-backed cart with real stock validation and coupon application.

Cart upsert: addToCart(userId, variantId, quantity): upsert the CartItem, but first validate current stock > 0 and requested quantity ≤ stockQuantity. Use a Prisma transaction: fetch variant + check stock + upsert cart item atomically.
Cart summary: getCartSummary(userId): Promise<CartSummary> — type includes: items: CartItemWithDetails[], subtotal: Decimal, appliedCoupon: Coupon | null, discountAmount: Decimal, finalTotal: Decimal. Computed in service layer, not Prisma query.
Coupon Zod schema: ApplyCouponSchema = z.object({ code: z.string().min(1).max(20).toUpperCase() }). The service validates all business rules and returns a typed CouponApplicationResult: { discount: Decimal; coupon: Coupon } | { error: CouponError }.
Coupon types: PERCENTAGE with max cap: const raw = subtotal.times(coupon.value).div(100); const discount = coupon.maxDiscount ? Decimal.min(raw, coupon.maxDiscount) : raw. FLAT: const discount = Decimal.min(coupon.value, subtotal). Use decimal.js for all.
03
Order Management
// 22 marks
▼

Order placement with atomic stock decrement and status machine.

Place order transaction: In one Prisma interactive transaction: (1) fetch cart items with variants, (2) call updateMany for each variant with stock check, (3) if any returns count=0, throw and roll back, (4) create Order + OrderItems (snapshot variant name + price), (5) increment coupon usedCount, (6) clear cart. All or nothing.
Order item snapshot: TypeScript: the OrderItem model has snapshotVariantName String and snapshotUnitPrice Decimal. Set these at order placement: snapshotVariantName: variant.variantName, snapshotUnitPrice: variant.sellingPrice. These never change even if the variant is edited later.
Status transition service: transitionOrderStatus(orderId, newStatus, userId, role). TypeScript: define valid transitions as const VALID_TRANSITIONS: Record<OrderStatus, OrderStatus[]> = { PENDING: ['CONFIRMED', 'CANCELLED'], CONFIRMED: ['SHIPPED', 'CANCELLED'], ... }. Check before updating.
Cancel + restock: Cancellation uses updateMany with { increment: quantity } for each variant — the same atomic pattern as decrement but in reverse.
04
Reviews & Filtering
// 18 marks
▼

Product reviews with purchase verification and Prisma full-text search.

Review eligibility: canReview(userId, productId) checks: user has a DELIVERED order containing a variant of this product. Prisma query: prisma.orderItem.findFirst({ where: { order: { userId, status: 'DELIVERED' }, variant: { productId } } }).
Average rating: Use Prisma's aggregate: prisma.review.aggregate({ where: { productId }, _avg: { rating: true }, _count: true }). Include in product response as averageRating: number | null; reviewCount: number.
Product search with Prisma full-text: Use PostgreSQL full-text search via Prisma: where: { name: { search: query }, description: { search: query } }. Requires the previewFeatures = ['fullTextSearch'] flag in Prisma schema.
Pagination: Implement cursor-based pagination for reviews (sorted by createdAt desc). Offset pagination for products (up to 100 per page). Document in README why cursor-based is better for the review list.
05
Testing & Docker
// 16 marks
▼

Inventory correctness tests and one-command startup.

Inventory unit tests: 6 Jest tests: (a) updateMany returns count=1 for valid decrement → success, (b) returns count=0 → throws OutOfStockError, (c) order with 3 items where item 2 fails → all decrements rolled back, (d) cancel order increments all variant stocks, (e) coupon PERCENTAGE with cap: 20% of 1000 capped at 150 = 150, (f) coupon FLAT larger than subtotal: discount = subtotal.
Coupon edge case tests: Test with decimal.js: 20% of ₹1000 = ₹200.00 exactly (not 199.9999999). Test flat coupon of ₹500 on ₹300 subtotal = ₹300 discount (discount cannot exceed subtotal).
docker-compose: api (Node), postgres (with health check), optional redis. Entrypoint: npx prisma migrate deploy && node dist/index.js. All env vars in .env.example with descriptions.
OpenAPI: Use @fastify/swagger + @fastify/swagger-ui. Register all routes with Zod-derived JSON schemas. Accessible at /docs with live 'Try it out' functionality.
// 02 · Design Questions
Answer in README.md

Node.js-specific design patterns — these come up in every backend interview.

Q1
Your order placement uses a Prisma interactive transaction with up to 50 updateMany calls (one per cart item). Is this a performance concern? What is the maximum number of database round trips inside one Prisma interactive transaction, and how does this affect latency?
Q2
The updateMany atomic stock decrement returns a count. If it returns 0, you throw an error and the transaction rolls back. But what if the database is under high load and the query times out before returning? Does Prisma roll back the transaction automatically?
Q3
You build the Prisma where clause dynamically from filter params. TypeScript: const where: Prisma.ProductWhereInput = {}. When you add where.category = category conditionally, is this type-safe? What happens if you add a field that doesn't exist on ProductWhereInput?
Q4
Prisma's @@check constraint prevents stockQuantity from going below 0 at the DB level. But your service also validates this. Is the DB constraint redundant? What is the correct layering of validation: Zod (input) → service (business rules) → DB constraint (integrity guarantee)?
