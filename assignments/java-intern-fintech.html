// The Problem
FinSmart helps users understand their money. A user can have multiple accounts (savings, checking, credit card). They log transactions against each account: income or expense, with a category and date. They set monthly budgets per category, and the app tracks how much of each budget has been used. They can also create savings goals and make deposits toward them.

Critical rule: use BigDecimal with ROUND_HALF_UP for every monetary calculation. A single floating-point rounding error in a financial app is a bug, not an edge case. Store money as NUMERIC(19,4) in PostgreSQL.

01
Account & Transaction Management
// 22 marks
▼

The core of the app. Users have accounts; transactions belong to accounts.

TransactionService.java — atomic balance updateService
@Transactional
public TransactionDto createTransaction(CreateTransactionRequest req) {
    Account account = accountRepository.findByIdAndUser(req.accountId(), currentUser())
        .orElseThrow(() -> new ResourceNotFoundException("Account not found"));

    Transaction tx = Transaction.builder()
        .account(account).amount(req.amount())
        .type(req.type()).category(req.category())
        .description(req.description()).transactionDate(req.date()).build();

    // update balance atomically
    if (req.type() == TransactionType.INCOME) {
        account.setBalance(account.getBalance().add(req.amount()));
    } else {
        account.setBalance(account.getBalance().subtract(req.amount()));
    }
    transactionRepository.save(tx);
    accountRepository.save(account);
    return transactionMapper.toDto(tx);
}
Account entity: Fields: name (e.g., 'HDFC Savings'), type (SAVINGS, CHECKING, CREDIT_CARD, CASH), currency (default INR), currentBalance (BigDecimal), user (owner). Balance starts at 0. Balance is computed from transactions — do not store it separately except as a cached value that gets updated on every transaction. Color-code field (hex string, optional, for UI).
Transaction entity: Fields: account, amount (BigDecimal, always positive), type (INCOME, EXPENSE), category (enum: FOOD, TRANSPORT, ENTERTAINMENT, SALARY, RENT, MEDICAL, SHOPPING, UTILITIES, OTHER), description, transactionDate (LocalDate), createdAt. A transaction belongs to exactly one account and one user.
APIs: POST /api/accounts — create. GET /api/accounts — list user's accounts with current balance. POST /api/transactions — create transaction and update account balance atomically (in a single @Transactional method). PUT /api/transactions/{id} — edit (recalculate balance). DELETE /api/transactions/{id} — delete (recalculate balance). GET /api/transactions?accountId=&category=&from=&to=&page=&size= — paginated with filters.
Balance integrity: Account balance must always equal: SUM(INCOME transactions) - SUM(EXPENSE transactions). Write a validation method validateBalanceIntegrity(UUID accountId) in your service that recalculates and compares. Use this in your integration tests.
02
Budget Management
// 20 marks
▼

Users set monthly spending limits per category. The app tracks usage and flags when over budget.

Budget entity: Fields: user, category, month (LocalDate — store as first day of month, e.g., 2026-06-01), limitAmount (BigDecimal). One budget per user per category per month. @UniqueConstraint(columnNames = {"user_id", "category", "month"}).
Budget usage calculation: GET /api/budgets?month=2026-06 — return all budgets for the given month with: limitAmount, spentAmount (sum of EXPENSE transactions in that category in that month), remainingAmount, usagePercentage (0–100), status: ON_TRACK / WARNING (>80%) / OVER_BUDGET (>100%).
Budget creation: POST /api/budgets — create or update (upsert). If a budget for this category+month already exists, update the limitAmount. Return the existing budget if no change.
Budget vs actual report: GET /api/budgets/summary?month=2026-06 — return total budgeted vs total spent for that month, plus a list of all budget items with status. Include categories that have spending but no budget set (show as “No budget”). Sort: OVER_BUDGET first, then WARNING, then ON_TRACK, then no-budget.
// Note

Use @Query in your repository to sum transactions by category and month in one DB call, not a loop in Java.

03
Savings Goals
// 20 marks
▼

Users create savings goals and deposit money toward them over time.

Goal projected date calculationLogic
// Calculate average daily deposit rate (last 30 days)
BigDecimal recentDeposits = goalDepositRepository
    .sumDepositsSince(goalId, LocalDate.now().minusDays(30));
if (recentDeposits.compareTo(BigDecimal.ZERO) == 0) return null;

BigDecimal dailyRate = recentDeposits.divide(
    new BigDecimal("30"), 4, RoundingMode.HALF_UP);
BigDecimal remaining = goal.getTargetAmount().subtract(goal.getCurrentAmount());
long daysNeeded = remaining.divide(dailyRate, 0, RoundingMode.CEILING).longValue();
return LocalDate.now().plusDays(daysNeeded);
Goal entity: Fields: name, targetAmount, currentAmount (BigDecimal, starts at 0), targetDate (LocalDate), status (ACTIVE, ACHIEVED, ABANDONED), createdAt, user. When currentAmount >= targetAmount, auto-set status to ACHIEVED.
Goal deposit: POST /api/goals/{id}/deposit — body: {amount, note}. Deduct amount from a specified account (user provides accountId in request). Increment goal's currentAmount. Store as a GoalDeposit record: goalId, accountId, amount, depositDate, note. If after deposit currentAmount >= targetAmount, set status ACHIEVED.
Goal progress: GET /api/goals/{id} — return: all fields, progress percentage, amount remaining, days remaining until targetDate, projected completion date based on average deposit rate (last 30 days average deposit / day → days until full). If no deposits yet, projected date is null.
Goal list: GET /api/goals?status=ACTIVE — list user's goals filtered by optional status. Return progress % for each. Sort by targetDate ascending (soonest deadline first).
04
Expense Analytics & Reports
// 20 marks
▼

This is where the data becomes useful. Users want to understand their spending patterns.

Monthly summary: GET /api/reports/monthly?year=2026&month=6 — return: totalIncome, totalExpenses, netSavings (income - expenses), top 3 spending categories with amounts and % of total expenses, daily average expense, highest single expense (amount, category, description, date).
6-month trend: GET /api/reports/trend?months=6 — last N months (default 6) of income vs expense per month. Return as a list sorted oldest-to-newest: [{month: '2026-01', income: 50000, expenses: 38000, net: 12000}, ...]. Compute from transactions, not stored separately.
Category breakdown: GET /api/reports/categories?from=2026-01-01&to=2026-06-30 — for the date range, return each category with total spent, % of total, transaction count, average transaction amount. Sort by total spent descending.
Cash flow by account: GET /api/reports/accounts/cash-flow?month=2026-06 — for each account: opening balance (balance at start of month), total credits, total debits, closing balance. Verify: closing = opening + credits - debits.
// Note

Use @Query with aggregation in repository. Do not load all transactions into memory to calculate — let the database do the grouping and summing.

05
Recurring Transactions & Testing
// 18 marks
▼

Automated recurring entries and the testing strategy that proves correctness.

Recurring transaction entity: Fields: user, account, type, category, amount, description, frequency (DAILY, WEEKLY, MONTHLY), dayOfMonth (for MONTHLY, e.g., 1–28), nextDueDate, isActive. Example: salary of ₹50,000 credited monthly on the 1st.
Scheduled processing: Use @Scheduled(cron = '0 0 8 * * ?') to run every morning at 8AM. For each active recurring transaction where nextDueDate <= today: create the actual transaction, update nextDueDate (add frequency period). Wrap each in a try-catch; if one fails, log it and continue to the next.
Management APIs: POST /api/recurring-transactions — create. PUT /api/recurring-transactions/{id}/toggle — activate/deactivate. GET /api/recurring-transactions — list user's recurring items with nextDueDate.
Unit tests: Test TransactionService: (a) createTransaction INCOME increases balance, (b) createTransaction EXPENSE decreases balance, (c) delete transaction recalculates balance correctly, (d) user cannot access another user's account (throw AccessDeniedException), (e) budget overspend sets status to OVER_BUDGET, (f) goal currentAmount >= target sets status ACHIEVED. 6 tests minimum.
// Note

For the scheduled job, use a service method annotated @Transactional per recurring transaction processing, not one big transaction for all. That way a single failure does not roll back successful ones.

// 02 · Design Questions
Answer in README.md

Four questions. Write concise answers — these come up in the review call.

Q1
A user deletes a transaction from March 2026 today (June 2026). Their account balance changes. Their March budget usage percentage also changes. Their savings goal deposit history changes. What cascading updates need to happen? How do you ensure consistency without a big monolithic delete method?
Q2
You store account balance as a field and update it on every transaction. But what if two transactions are created at the same time (concurrent requests)? How does your code handle this? What database feature prevents a race condition on the balance field?
Q3
Why should you NEVER use `double` or `float` for monetary calculations in a financial application? Give a specific example of a calculation where `double` produces the wrong answer that `BigDecimal` gets right.
Q4
The 6-month trend API does a GROUP BY query on the transactions table. If a user has 50,000 transactions, is this query fast? What index would you add, and on which columns?
