// The Problem
ConnectHub Node.js uses cursor-based pagination for the feed (more efficient than offset at scale). The follow status is a TypeScript discriminated union returned by a service method. Like count updates use Prisma's atomic increment operator — never a fetch-then-update pattern. Notification creation is fire-and-forget using process.nextTick so it does not block the main response.
// 01 · Modules
Five Modules — 100 Marks

TypeScript strict mode throughout. No any. Every Zod schema exported from a schemas/ folder. Every Prisma query wrapped in a typed service class.

01
User Profile & Auth
// 20 marks
▼

Fastify JWT auth with Prisma user management.

Auth setup: Use @fastify/jwt. Register with secret from env. Add fastify.decorate('authenticate', ...) that verifies the JWT and attaches req.user: { id: string, role: Role }. Protected routes add preHandler: [fastify.authenticate].
Registration: Zod: RegisterSchema = z.object({ username: z.string().min(3).max(30).regex(/^[a-zA-Z0-9_]+$/), email: z.string().email(), password: z.string().min(8) }). Hash with bcrypt. Catch Prisma P2002 for duplicate username/email and return typed error.
Profile response type: Define: type ProfileResponse = BaseProfile & ({ isPrivate: false } | { isPrivate: true; isFollowing: boolean; followStatus: FollowStatus | null }). For private accounts, include whether the viewer is following. For public accounts, omit follow status entirely.
Search: GET /api/users/search?q=X using Prisma mode: 'insensitive': where: { OR: [{ username: { contains: q, mode: 'insensitive' } }, { displayName: { contains: q, mode: 'insensitive' } }] }.
02
Follow System
// 22 marks
▼

Follow/unfollow with Prisma enum and TypeScript discriminated union for status.

Follow status type: TypeScript: type FollowState = { status: 'NOT_FOLLOWING' } | { status: 'PENDING'; requestId: string } | { status: 'APPROVED'; since: Date } | { status: 'BLOCKED' }. The getFollowState(followerId, followingId) method returns this union.
Follow service: follow(followerId, followingUsername): validate not self, check current state using getFollowState, throw typed errors for invalid transitions. Create follow with status APPROVED (public) or PENDING (private). Return the new FollowState.
Follow request management: approveRequest(requestId, ownerId): verify the request's followingId === ownerId. Update status to APPROVED. rejectRequest: delete the Follow record.
Follower count: Use Prisma's _count relation: prisma.user.findUnique({ where: { id }, select: { _count: { select: { followers: { where: { status: 'APPROVED' } }, following: { where: { status: 'APPROVED' } } } } } }).
03
Posts & Visibility
// 22 marks
▼

Post creation with Prisma soft delete and visibility enforcement.

Post visibility query: A helper buildPostVisibilityWhere(viewerId: string): Prisma.PostWhereInput returns the appropriate WHERE clause based on: public posts on any account, FOLLOWERS_ONLY posts on accounts where viewerId is an APPROVED follower, PRIVATE posts only by the post author.
Like count atomic update: likePost(userId, postId): create a PostLike record, then use prisma.post.update({ where: { id: postId }, data: { likeCount: { increment: 1 } } }). Both in a Prisma transaction. Catch P2002 on the PostLike unique constraint to handle duplicate likes.
Soft delete: Add deletedAt DateTime? to Post. Add a Prisma Client Extension that modifies all post.findMany and post.findUnique queries to add where: { deletedAt: null } automatically. Verify this works in a test.
Comment tree: GET /api/posts/:id/comments returns top-level comments with replies included: prisma.comment.findMany({ where: { postId, parentId: null }, include: { replies: { take: 5, orderBy: { createdAt: 'asc' } } } }).
04
Feed & Notifications
// 20 marks
▼

Cursor-based feed pagination and typed notification creation.

Cursor-based feed: getFeed(userId, cursor?: string, limit = 20): prisma.post.findMany({ where: buildFeedWhere(userId), take: limit + 1, skip: cursor ? 1 : 0, cursor: cursor ? { id: cursor } : undefined, orderBy: { createdAt: 'desc' } }). If results.length > limit, the last item is the next cursor (remove it from the returned data).
Notification factory: Create a NotificationFactory class with static methods: static newFollower(actorId, recipientId): CreateNotificationDto, static postLiked(actorId, recipientId, postId), etc. The notification content is pre-formatted in the factory. Services call the factory, not inline string construction.
Notification creation side effect: In FollowService.follow(), after creating the follow record, call notificationService.create(NotificationFactory.newFollower(...)). Do NOT await this — fire and forget. Use process.nextTick(() => notificationService.create(...)) or Fastify's background task pattern so notification creation does not block the follow response.
Unread count: GET /api/notifications/unread-count returns { count: number }. Simple: prisma.notification.count({ where: { recipientId, isRead: false } }). This endpoint is called frequently — it should be extremely fast.
05
Hashtags & Testing
// 16 marks
▼

Hashtag extraction, post tagging, and unit tests for the visibility logic.

Hashtag parsing: extractHashtags(content: string): string[] using a regex: content.match(/#[a-zA-Z][a-zA-Z0-9_]*/g)?.map(t => t.slice(1).toLowerCase()) ?? []. On post create, upsert each hashtag and create PostHashtag join records in one Prisma transaction.
Trending hashtags: GET /api/hashtags/trending?limit=10 using Prisma groupBy on PostHashtag filtered to last 24 hours: prisma.postHashtag.groupBy({ by: ['hashtagId'], where: { post: { createdAt: { gte: oneDayAgo } } }, _count: true, orderBy: { _count: { hashtagId: 'desc' } }, take: limit }).
Unit tests: 6 tests for FollowService: (a) follow public account → APPROVED, (b) follow private → PENDING, (c) follow self → throws, (d) double follow → throws AlreadyFollowing, (e) getFollowState returns correct union variant, (f) block user removes existing follow relationship.
Visibility test: Test buildPostVisibilityWhere: given a viewerId, assert the WHERE clause structure is correct for viewing another user's posts. Use Jest's expect(result).toMatchObject({...}) to verify the nested Prisma where object shape.
// 02 · Design Questions
Answer in README.md

Node.js-specific design patterns — these come up in every backend interview.

Q1
Cursor-based pagination uses the last item's ID as the cursor for the next page. But if a new post is created between page 1 and page 2 fetches, it might appear at the top of page 1 in a re-fetch but not in page 2. Is this a problem for a social media feed? How does Instagram/Twitter handle this?
Q2
You fire-and-forget notification creation with process.nextTick(). If the notification creation throws an error, it's caught by an uncaughtRejection handler but the follow response has already been sent as success. Should notification creation failure cause the follow to fail? Make the argument for and against.
Q3
Your Prisma Client Extension adds WHERE deletedAt IS NULL to all Post queries. But what about queries that explicitly need to find deleted posts (e.g., an admin moderation endpoint)? How do you bypass the extension for those queries?
Q4
The buildPostVisibilityWhere function returns a complex nested Prisma WHERE object. This object is tested via toMatchObject. But the real proof is whether it actually filters correctly in the database. Why is a pure unit test of the WHERE object insufficient, and what kind of test actually verifies the visibility rules?
