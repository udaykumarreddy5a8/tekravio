01
Test Framework Design & Architecture
// 15 marks · The foundation — evaluated first

Before writing a single test, design the framework. At 8 years, this is what separates you from a junior automation engineer. The structure must be maintainable, scalable, and onboardable by a new team member in under an hour.

Project structure — clear separation: framework/ (base classes, utilities, config), tests/api/, tests/e2e/, tests/performance/, data/, reports/
Base classes — BaseTest.java with setup/teardown, driver init, auth token management. No repeated boilerplate in test classes.
Config abstraction — environment-specific config (dev / staging / prod) loaded from config.properties or YAML. Zero hardcoded URLs or credentials anywhere in code.
Test data management — test data loaded from external JSON/CSV files, not hardcoded in tests. Data builder pattern for complex objects (Patient, Prescription, Schedule).
Reporting — Allure or ExtentReports with screenshots on failure, API request/response logged, test categorisation by severity (Smoke / Regression / E2E).

02
API Test Automation — Full Coverage
// 25 marks · Highest weight — this is core SDET work

Write comprehensive API tests using RestAssured with Cucumber BDD. At this level, we expect happy path, negative cases, boundary values, schema validation, and chained test flows — not just status code assertions.

Auth module tests — register (valid + duplicate + invalid email), login (valid + wrong password + account disabled), token refresh (valid + expired + tampered), logout (valid + already-logged-out)
Patient CRUD tests — create (valid + missing required fields + duplicate email), read (own profile + other patient's profile as Patient role = 403), update, delete (cascades to schedules?)
Prescription upload tests — valid image upload + S3 URL returned, file too large (>10MB), unsupported file type, missing patient ID, Textract extraction verified in response body
Reminder schedule tests — create schedule, snooze (valid timings + invalid timing), mark taken (idempotency — can you mark taken twice?), adherence calculation accuracy for edge dates
Contract / schema validation — every API response validated against JSON Schema. Any schema mismatch fails the test immediately.
BDD feature files — at least auth, patient, and reminder flows written as Gherkin .feature files with step definitions
PatientApiTests.java (sample pattern)JAVA
@Test(groups = "regression")
@Description("Patient cannot access another patient's profile")
public void patient_cannotAccessOtherPatientProfile() {
    var token = AuthHelper.getPatientToken("alice@test.com");
    var otherPatientId = TestData.get("other_patient_id");

    given()
        .header("Authorization", "Bearer " + token)
    .when()
        .get("/api/v1/patients/" + otherPatientId)
    .then()
        .statusCode(403)
        .body("error", notNullValue())
        .body(matchesJsonSchemaInClasspath("schemas/error-response.json"));
}
// What We Look For

We count the negative test cases. Any senior SDET who writes only happy-path tests is not operating at this level. We expect at least 3 negative cases per endpoint.

03
Performance Testing — Load, Stress & Spike
// 20 marks · Non-functional quality

This is a healthcare reminder system. If it slows down under load, reminders are delayed and patients miss doses. Performance is not optional. Design and run meaningful performance tests against the critical paths.

Tool choice — k6 (JavaScript-based, developer-friendly, CI-compatible) OR JMeter OR Gatling. Justify your choice in the README.
Baseline test — 10 concurrent users for 5 minutes on the login + get schedule + mark taken flow. Establish baseline response times and error rate.
Load test — ramp to 100 concurrent users over 5 minutes, hold for 10 minutes, ramp down. Monitor: p95 response time, error rate, throughput.
Stress test — push to 500 concurrent users. Find the breaking point. Document where the system degrades and what breaks first (API timeout? DB connections? FCM rate limit?).
Spike test — simulate a sudden 10x spike (10 → 100 users in 30 seconds) to simulate a viral hiring post scenario.
Performance report — HTML report with p50/p95/p99 response times, throughput graph, error rate over time, and your pass/fail verdict with thresholds.
// k6 Recommended

k6 integrates cleanly with GitHub Actions, outputs JSON results that can be parsed for quality gates, and scripts are version-controllable. Thresholds in k6: http_req_duration: ['p95 < 500'] — fail the pipeline if p95 exceeds 500ms.

04
Security Testing — OWASP Healthcare Checks
// 15 marks · Non-negotiable in healthcare

This application handles prescription data and medical records. Security testing is mandatory — not optional, not aspirational. At 8 years experience, you are expected to know what to look for without being told every vulnerability.

JWT security checks — test with: expired token (should 401), tampered payload (should 401), algorithm confusion (alg:none attack), token reuse after logout
Authorization tests — horizontal privilege escalation: Patient A accessing Patient B's prescriptions, schedules, reminder logs. Document every endpoint that should return 403 and verify each one.
Input validation — SQL injection attempts in patient name/email fields, XSS payloads in text inputs, oversized payloads (20MB file upload), null byte injection in file names
Sensitive data exposure — verify passwords are never returned in any API response, prescription S3 URLs are pre-signed with expiry (not permanent public URLs), error messages don't leak stack traces or internal paths
OWASP ZAP scan — run an authenticated passive scan against the running API. Export the HTML report. Document which findings you'd raise as P1/P2/P3 defects and which are false positives.
// Document Your Findings Honestly

If you find a real vulnerability in the provided test system, document it clearly in your README with steps to reproduce. Finding real issues scores higher than a clean ZAP report with no findings. That just means you didn't look hard enough.

05
E2E Test Suite — Critical User Journeys
// 15 marks · End-to-end coverage

Write E2E tests covering the three most critical user journeys. Use Selenium with Java or Playwright. These should test the full stack — frontend → API → database state verification.

Journey 1 — Prescription to Reminder: Login as patient → upload prescription image → verify Textract extraction in UI → confirm medicine schedule created → verify reminder appears in dashboard
Journey 2 — Reminder Interaction: Login as patient → navigate to today's reminders → mark a reminder as taken → verify adherence % updates in dashboard → verify reminder_log entry via API call
Journey 3 — Admin Oversight: Login as admin → view patient list → open a patient's prescription history → verify all uploaded prescriptions are listed with correct S3 metadata → deactivate patient → verify patient cannot log in
Page Object Model — every UI interaction abstracted into page objects. Test methods contain zero raw selectors.
Screenshot on failure — automatic screenshot captured and embedded in Allure report on any test failure
06
CI/CD Pipeline + Quality Gates
// 10 marks · Ship quality, not bugs

A test suite that isn't in CI is not a test suite — it's a hobby project. Wire everything into GitHub Actions with meaningful quality gates that would actually block a bad build from shipping.

On every PR — run smoke API tests (auth + patient CRUD). Fail the PR if any smoke test fails. Run time must be under 3 minutes.
On merge to main — run full API regression suite + E2E critical journeys. Publish Allure report as GitHub Pages artifact.
Nightly scheduled run — run full regression + performance baseline. If p95 degrades more than 20% from previous baseline, send a Slack/email alert.
Quality gates — define and enforce: API test pass rate ≥ 95%, E2E pass rate ≥ 90%, p95 response time < 500ms, zero P1 security findings. Build fails if any gate is breached.
Test parallelisation — API tests must run in parallel (TestNG parallel=methods or k6 VUs). Full regression must complete in under 8 minutes.
