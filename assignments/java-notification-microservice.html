Design and build a channel-agnostic Notification Microservice using Java 17+ and Spring Boot 3.x. Email, SMS, WhatsApp, Push — one service that handles all channels asynchronously, reliably, and at scale. This is not a tutorial project. We want to see the decisions a senior engineer makes.

// The Objective
Build a standalone, reusable Notification Microservice that any application or business domain can integrate with. The service exposes REST APIs to submit notifications, tracks their status through the full lifecycle (PENDING → SENT / FAILED), and processes them asynchronously via Kafka. Supported channels: Email, SMS, WhatsApp, and Push Notifications.

We evaluate this on three things: clean architecture (can we drop in a new channel in under 30 minutes?), fault tolerance (what happens when SendGrid is down?), and production readiness (can this run in a real Kubernetes cluster tomorrow?). Every design decision you make will be discussed in the review call.

01
Domain Model, REST API & OpenAPI Documentation
// 18 marks · The contract everything is built on

The API contract and domain model are the foundation. A wrong decision here propagates to every layer. Design it carefully — then defend every choice in your README.

// Notification Request Model

Design the generic NotificationRequest DTO. It must work across all channels without being channel-specific. Every field must have validation annotations.

NotificationRequest.javaDTO
@NotNull String notificationId;       // UUID, idempotency key
@NotBlank String recipientId;          // user/device identifier
RecipientDetails recipient;            // email, phone, deviceToken, etc
@NotNull ChannelType channel;          // EMAIL | SMS | WHATSAPP | PUSH
String subject;                        // optional, email only
@NotBlank String messageContent;       // or templateId + variables
String templateId;                     // optional — overrides messageContent
Map<String, String> templateVariables; // {{name}}, {{orderId}}
@NotNull Priority priority;            // HIGH | MEDIUM | LOW
Map<String, Object> metadata;         // arbitrary context
Instant scheduledAt;                   // null = send immediately
// REST Endpoints — Implement All Four
POST /api/v1/notifications — Submit a notification. Returns 202 Accepted with a notificationId. Must be idempotent — re-submitting the same notificationId must not create a duplicate.
GET /api/v1/notifications/{id}/status — Return current status, channel, timestamps (submitted, processed, delivered/failed), and retry count.
POST /api/v1/notifications/{id}/retry — Manually trigger a retry for a FAILED notification. Should not be callable on SENT notifications. Returns 409 if already sent.
GET /api/v1/notifications/history — Paginated notification history with filters: recipientId, channel, status, dateRange. Sorted by createdAt desc. Page size max 100.
OpenAPI / Swagger: Full Swagger UI accessible at /swagger-ui.html. Every endpoint, request body, response, and error code must be documented. No undocumented endpoints.
// Status Lifecycle
Implement the full status state machine: PENDING → PROCESSING → SENT (terminal), PENDING → PROCESSING → FAILED → RETRYING → SENT or FAILED (terminal after max retries). Invalid transitions (e.g. SENT → RETRYING) must throw an exception, not silently fail.
Every status change must be timestamped and persisted. The audit trail is non-negotiable.
// Senior Signal

Idempotency on the POST endpoint is what separates a senior engineer's API from a junior one. A network retry should not send the same customer a duplicate order confirmation. Your README should explain your idempotency strategy and where it could still fail.

02
Channel Adapters — Strategy Pattern Implementation
// 20 marks · The extensibility test

This is the core extensibility challenge. We will evaluate: can we add a new channel (say, Slack) in 30 minutes by adding one class without touching existing code? If the answer is yes, you've passed this task.

// NotificationSender Interface
NotificationSender.javaInterface
public interface NotificationSender {
    ChannelType supports();
    NotificationResult send(NotificationMessage message);
    default boolean canHandle(ChannelType type) {
        return supports().equals(type);
    }
}
// Implement All Four Adapters
EmailAdapter: Integrate with SendGrid or AWS SES. Support HTML and plain text. Handle bounces and delivery failures distinctly — a bounce should not trigger the same retry logic as a transient failure.
SmsAdapter: Twilio or AWS SNS. Validate phone number format before dispatch. Handle international numbers. Rate limit awareness — if Twilio returns 429, back off.
WhatsAppAdapter: Meta WhatsApp Business API or Twilio for WhatsApp. Support template messages (required for outbound on Meta). Mock-able for local development without a Meta account.
PushNotificationAdapter: Firebase Cloud Messaging. Support both single-device (token) and topic-based notifications. Handle expired/invalid tokens gracefully — remove them from the system, not just log and continue.
NotificationSenderFactory: A @Component that injects all NotificationSender implementations and returns the correct one by channel type. New adapters must auto-register without any factory code change.
// Provider Fallback
For Email: if SendGrid fails with a 5xx, fall back to AWS SES automatically. The caller should not know which provider was used. Document the fallback strategy in your README — when does it trigger, how many times, what's the circuit breaker threshold?
Implement a MockNotificationSender that activates when a Spring profile local is active. It logs the notification and returns success without calling any external provider. This is mandatory — reviewers run the project locally.
// What We're Actually Evaluating

We will add a SlackAdapter class during the code review and see how long it takes to wire up. If it requires changes to more than one existing class, it's not extensible enough. Open/Closed Principle — this task is entirely about that.

03
Kafka-Based Async Pipeline & Dead Letter Queue
// 20 marks · The reliability test

Every notification goes through Kafka. No direct-to-provider calls from the REST layer. The REST API accepts the request and publishes to Kafka within 500ms. Everything after that is asynchronous.

// Topic Design
Channel-specific topics: notifications.email, notifications.sms, notifications.whatsapp, notifications.push. Justify your partition count in the README — how many parallel consumers do you expect per channel?
Priority routing: HIGH priority notifications should not be blocked by a queue of LOW priority ones. Design a topic or partition strategy that ensures HIGH priority messages are processed first. Explain trade-offs in your README.
Dead Letter Queue: After max.retry.attempts failures on a channel topic, messages go to notifications.{channel}.dlq. The DLQ must be monitored — an Actuator endpoint should expose DLQ depth as a metric.
// Consumers
One consumer per channel using @KafkaListener with a @KafkaHandler. Consumers are independently scalable — email volume may be 10x SMS volume.
Concurrent consumers: Configure concurrency on each listener. Email listener: concurrency=3. SMS: concurrency=2. Push: concurrency=5. These should be externalised in application.yml.
Consumer error handling: Use Spring Kafka's DefaultErrorHandler with a DeadLetterPublishingRecoverer. A deserialization failure must go to DLQ immediately — not retried. A provider failure should be retried.
Message ordering: Explain in your README whether ordering matters for notifications and how your Kafka design handles (or intentionally ignores) ordering guarantees.
// Retry with Exponential Backoff
Configurable retry count (default: 3) and initial delay (default: 1s), with exponential backoff (multiplier: 2). After max retries, route to DLQ and mark notification as FAILED.
Retries for transient errors (5xx, timeout) must be distinguishable from permanent failures (invalid email, invalid phone). Permanent failures must go to DLQ immediately — no retries.
application.yml — Kafka config sampleConfig
tekravio:
  notification:
    retry:
      max-attempts: 3
      initial-interval: 1000
      multiplier: 2.0
      max-interval: 30000
    kafka:
      topics:
        email: notifications.email
        sms: notifications.sms
        whatsapp: notifications.whatsapp
        push: notifications.push
        dlq-suffix: .dlq
      consumers:
        email-concurrency: 3
        push-concurrency: 5
04
Template Management Engine
// 15 marks · Dynamic content at scale

Hard-coded messages don't scale. Build a template management system that supports dynamic placeholders, template versioning, and multi-channel templates — all backed by the DB and cached in Redis.

Template CRUD APIs: POST /api/v1/templates, GET /api/v1/templates/{id}, PUT /api/v1/templates/{id}, DELETE /api/v1/templates/{id}. ADMIN role only for create/update/delete.
Dynamic placeholders: Support Mustache-style {{variableName}} syntax. At send time, resolve variables from NotificationRequest.templateVariables. Fail clearly (not silently) if a required variable is missing — return a 400 with the missing variable names.
Template versioning: Each template has a version number. PUT /api/v1/templates/{id} creates a new version, it does not overwrite. The request can specify a version — default is latest. Previous versions are readable but not sendable unless explicitly specified.
Channel-aware templates: A template can have variants per channel. The ORDER_SHIPPED template has an email variant (HTML, subject), an SMS variant (160 char limit warning), and a push variant (title + body). One templateId, multiple channel outputs.
Redis caching: Templates are cached in Redis with a 10-minute TTL. Cache is invalidated on template update. Cache key: template:{id}:v{version}. Implement with Spring Cache @Cacheable and @CacheEvict.
Preview endpoint: POST /api/v1/templates/{id}/preview — accepts templateVariables and returns the rendered message for each channel without sending. Essential for debugging.
Example Template — ORDER_SHIPPEDMustache
// Email variant
Subject: Your order {{orderId}} is on its way!
Body (HTML):
<h2>Hi {{customerName}},</h2>
<p>Your order <strong>{{orderId}}</strong> has been shipped via {{courier}}.</p>
<p>Expected delivery: <strong>{{deliveryDate}}</strong></p>

// SMS variant (≤160 chars)
Hi {{customerName}}, order {{orderId}} shipped via {{courier}}. Delivery: {{deliveryDate}}

// Push variant
Title: Order Shipped!
Body: {{orderId}} is on its way. Expected: {{deliveryDate}}
05
Security — JWT Auth, Roles & PII Encryption
// 12 marks · Production cannot ship without this

A notification service handles recipient phone numbers, email addresses, and device tokens — all PII. Security is not optional, it's a gate condition. If this task is incomplete, the submission fails regardless of other scores.

JWT authentication: All endpoints except /actuator/health and /swagger-ui.html require a valid JWT. Implement JwtAuthenticationFilter using Spring Security. Token expiry: configurable, default 1 hour. Provide a POST /api/v1/auth/token endpoint for obtaining tokens in tests.
Role-based access control: Two roles: SERVICE (can submit notifications, check status, view history) and ADMIN (all SERVICE permissions + template management + retry any notification + DLQ inspection). Use Spring Security's @PreAuthorize annotations on service methods — not just controller layer.
PII encryption at rest: Recipient email, phone number, and device token must be encrypted in the database using AES-256. Decryption happens only within the adapter before dispatch. The database administrator seeing raw DB rows must not see plaintext PII. Implement as a JPA AttributeConverter.
Input validation: Email format validation, phone number format (E.164), device token length constraints. Validate at the DTO layer with Bean Validation. Return 400 with field-level error messages — never a 500 from an invalid input.
Rate limiting: Implement per-client rate limiting using a token bucket algorithm. Max 100 notifications per minute per JWT client. Return 429 with Retry-After header when exceeded. Use Redis for distributed rate limit state.
// Hard Gate

If we can call POST /api/v1/notifications without a JWT and it returns 200, this task scores 0. Security failures in a production microservice are not "partial credit" situations.

06
Testing — Unit, Integration & Contract Tests
// 10 marks · Untested code is unfinished code

We look at test quality, not test quantity. 10 well-thought-out tests that cover real edge cases score higher than 100 tests that only verify the happy path.

Unit tests with Mockito: All service layer classes must have unit tests. Mock all dependencies. Cover: successful send, channel adapter failure, retry trigger, max retries exceeded, idempotency (duplicate notificationId rejected), template variable missing, invalid channel type. Minimum 80% line coverage on service and domain packages — enforced by JaCoCo Maven plugin (build fails below threshold).
Integration tests with Testcontainers: At least 3 full-stack integration tests using Testcontainers (PostgreSQL + Kafka). Test the complete flow: HTTP request → Kafka publish → Consumer → Adapter (mocked external) → Status update → GET status returns SENT. These must pass in CI without any local setup beyond Docker.
Kafka consumer tests: Test the retry + DLQ flow end-to-end: inject a failing NotificationSender, verify retries exhaust, verify message lands in DLQ topic, verify notification status becomes FAILED.
Template engine tests: Test Mustache rendering: happy path, missing variable (expect exception), empty variable map, special characters in variables (SQL injection attempt via template variable must not reach the DB as executable SQL).
Security tests: Test that unauthenticated requests return 401, ROLE_SERVICE cannot access template management endpoints (expect 403), ROLE_ADMIN can. These tests must actually start the security context — not just mock it away.

Docker, Observability & README

A microservice that requires 45 minutes of tribal knowledge to run is not production-ready. One command. Everything up. That's the standard.

Dockerfile: Multi-stage build. Stage 1: Maven build. Stage 2: JRE 17 slim image. Final image must be under 300MB. Health check instruction in Dockerfile.

Spring Boot Actuator + Prometheus: /actuator/health returns aggregate health (DB, Kafka, Redis). Custom metrics: notifications.sent.total{channel}, notifications.failed.total{channel}, notifications.dlq.depth{channel}. These must appear in Prometheus format at /actuator/prometheus.
README.md: Contains: prerequisites, how to run locally (one command), how to obtain a JWT for testing, API examples with curl, environment variables reference, architecture diagram (text or image), and your design decisions section — at least 3 meaningful choices you made and why.

Schema Requirements

Design this schema yourself. The entities below are the minimum — you may add tables as needed. Use Flyway for migrations. Every migration file must be idempotent.

Core EntitiesPostgreSQL
-- notifications: core notification record
notifications (
  id UUID PRIMARY KEY,
  recipient_id VARCHAR(255),
  channel ENUM('EMAIL','SMS','WHATSAPP','PUSH'),
  status ENUM('PENDING','PROCESSING','SENT','FAILED','RETRYING'),
  priority ENUM('HIGH','MEDIUM','LOW'),
  template_id UUID NULLABLE,
  message_content TEXT -- encrypted PII removed to recipient table
  retry_count INT DEFAULT 0,
  max_retries INT DEFAULT 3,
  sent_at TIMESTAMP,
  failed_at TIMESTAMP,
  created_at TIMESTAMP,
  updated_at TIMESTAMP
)

-- recipients: PII stored separately, all columns AES-256 encrypted
notification_recipients (
  id UUID PRIMARY KEY,
  notification_id UUID REFERENCES notifications(id),
  email_encrypted VARCHAR(512),
  phone_encrypted VARCHAR(256),
  device_token_encrypted VARCHAR(512)
)

-- templates + versioning
notification_templates (
  id UUID, version INT,
  name VARCHAR(255), channel ChannelType,
  subject_template TEXT, body_template TEXT,
  is_active BOOLEAN, created_by VARCHAR,
  created_at TIMESTAMP,
  PRIMARY KEY (id, version)
)

-- audit trail: immutable log of every status change
notification_audit (
  id UUID PRIMARY KEY,
  notification_id UUID,
  from_status VARCHAR, to_status VARCHAR,
  reason TEXT, created_at TIMESTAMP

// 06 · Design Questions
Answer These in Your README

Short answers are fine. Vague answers score 0. We will ask follow-up questions on every answer in the review call.

Q1
Your Kafka consumer for email crashes mid-processing after reading a message but before marking it as SENT. When it restarts, what happens to that notification? How does your design prevent double-sending? Where can it still fail?
Q2
A client submits 10,000 notifications in 30 seconds. Your service is running one instance with concurrency=3 on the email consumer. Walk through what happens end-to-end. What's the first thing that breaks?
Q3
SendGrid is down for 20 minutes. Describe exactly what happens in your system during those 20 minutes and the 10 minutes after it comes back. What is the customer experience? What does the DBA see in the DB?
Q4
A compliance requirement arrives: all notification content (message body) must be deleted after 90 days. You have 50 million notification records. Walk through the schema changes, data migration strategy, and the scheduled job you'd write. What are the risks?
