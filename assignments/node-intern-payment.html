// The Problem
PayFlow Node.js uses Prisma interactive transactions for all payment flows. The idempotency pattern uses Prisma's unique constraint + catching P2002 error — no SELECT before INSERT. Payment status is a TypeScript discriminated union that the repository layer maps to/from Prisma's string enum. The X-Idempotency-Key header is validated by a Fastify preHandler hook.
// 01 · Modules
Five Modules — 100 Marks

TypeScript strict mode throughout. No any. Every Zod schema exported from a schemas/ folder. Every Prisma query wrapped in a typed service class.

01
Wallet Management
// 20 marks
▼

Wallet CRUD with atomic balance operations.

Wallet Prisma model: wallet model with balance Decimal @default(0) @db.Decimal(19,4), status WalletStatus @default(ACTIVE). Auto-create wallet on user creation using a Prisma middleware / post-create hook.
Credit / Debit methods: credit(userId: string, amount: Decimal, referenceId: string): Promise<Wallet> and debit(userId: string, amount: Decimal, referenceId: string): Promise<Wallet>. Both called inside a Prisma transaction by the PaymentService. Debit checks: if (wallet.balance.lt(amount)) throw new AppError('Insufficient balance', 422, 'INSUFFICIENT_BALANCE').
Top-up endpoint: POST /api/wallet/topup — Zod: { amount: z.number().positive().max(100000), method: z.enum(['UPI','CARD','NET_BANKING']), transactionRef: z.string() }. Calls wallet.credit() in a transaction.
Statement: Use TanStack Query on the frontend? No — this is a backend assignment. Implement the server-side: GET /api/wallet/statement paginated with cursor-based pagination (not offset) for efficiency on large datasets. Return { data, nextCursor }.
02
Payment Processing & Idempotency
// 25 marks
▼

Type-safe payment flow with idempotency handled via Prisma unique constraint.

Payment status type: TypeScript discriminated union: type PaymentState = { status: 'INITIATED' } | { status: 'PROCESSING' } | { status: 'SUCCESS'; processedAt: Date } | { status: 'FAILED'; failureReason: string; failedAt: Date }. The PaymentRepository maps Prisma's flat model to this union.
Idempotency via try/catch: In initiatePayment(idempotencyKey, dto): try to create the payment with a unique constraint on (userId, idempotencyKey). Catch Prisma's PrismaClientKnownRequestError with code === 'P2002' and fetch + return the existing payment. This avoids a separate SELECT before INSERT.
Payment flow: All in one Prisma interactive transaction: create payment (INITIATED), transition to PROCESSING, call wallet debit, set SUCCESS or FAILED. Use prisma.$transaction with a timeout: { timeout: 5000 }.
X-Idempotency-Key header: Add a Fastify hook: fastify.addHook('preHandler', async (req) => { if (req.routerPath === '/api/payments' && req.method === 'POST') { const key = req.headers['x-idempotency-key']; if (!key || typeof key !== 'string') throw new AppError('Missing idempotency key', 400) } }).
03
Refund Management
// 22 marks
▼

Refund lifecycle with Zod-validated eligibility and typed refund status.

Refund eligibility: validateRefundEligibility(paymentId: string, userId: string, amount: Decimal) returns Result<void, RefundError> using a simple Result type: type Result<T, E> = { ok: true; value: T } | { ok: false; error: E }. Check: payment SUCCESS, within 7 days, amount ≤ refundable.
Refund creation: On valid eligibility, create refund with status PENDING. Store originalAmount, requestedAmount, refundableAmount (original - already refunded amount from previous approved refunds) for audit.
Process refund (admin): approveRefund(refundId, adminId) in a Prisma transaction: credit wallet, set refund PROCESSED, increment payment's refundedAmount. Use Prisma's update with increment for the refundedAmount to avoid race conditions.
Refund types: TypeScript: type RefundType = payment.amount === payment.refundedAmount + refund.amount ? 'FULL' : 'PARTIAL'. Compute this in the service, not the controller.
04
Merchant & Statements
// 18 marks
▼

Merchant management and settlement reporting.

Merchant auth: Merchant users have role MERCHANT. Add a Fastify decorator: fastify.decorate('requireMerchant', async (req) => { if (req.user.role !== 'MERCHANT') throw new AppError('Forbidden', 403) }). Use with preHandler: [fastify.requireMerchant] on merchant routes.
Payment verification: GET /api/merchant/payments/verify?orderId=X — find payment where orderId = X AND merchantId = req.user.id. Return typed: type VerificationResult = { verified: boolean; status: PaymentStatus; amount?: Decimal; processedAt?: Date }.
Settlement report: Use Prisma groupBy on the transactions table grouped by DATE(createdAt) using a raw query or computed field. Aggregate: total amount, refunded amount, net per day.
Suspended merchant check: Add a Fastify hook specific to payment creation: check if the target merchant's status is SUSPENDED. If so, throw AppError('Merchant account suspended', 422, 'MERCHANT_SUSPENDED').
05
Testing & Error Handling
// 15 marks
▼

Idempotency tests, balance integrity tests, and typed error responses.

Idempotency unit test: Mock Prisma to throw PrismaClientKnownRequestError with code P2002 on payment create. Assert the service catches it and calls findUnique to return the existing payment. The response must be identical.
Balance integrity test: Test the wallet debit: mock prisma.wallet.findFirst to return balance 500. Call debit(amount=600). Assert InsufficientBalanceException thrown. Call debit(amount=400). Assert prisma.wallet.update called with data: { balance: { decrement: 400 } }.
Fastify error handler: Test the error handler via Fastify's inject method: POST to an endpoint that throws AppError(message, 422). Assert response: status 422, body { error: message, statusCode: 422 }.
Zod validation test: POST to /api/payments without the X-Idempotency-Key header. Assert 400 response with message 'Missing idempotency key'.
// 02 · Design Questions
Answer in README.md

Node.js-specific design patterns — these come up in every backend interview.

Q1
Prisma's P2002 error for the idempotency key means the unique constraint was violated. But P2002 fires for ANY unique constraint violation, not just the idempotency key. How do you check which unique field caused the violation to handle idempotency specifically vs other constraint violations?
Q2
You use a Prisma interactive transaction for the payment flow. The wallet debit succeeds, but then the Prisma write for the payment status update fails due to a network timeout. The transaction rolls back. But the wallet balance was modified inside the same transaction — does it roll back too? Why?
Q3
Cursor-based pagination for the wallet statement: you return a nextCursor (the ID of the last item in the current page). On the next request, the client sends ?cursor=X. How do you write the Prisma query for cursor-based pagination using the cursor approach?
Q4
Your payment status is a TypeScript discriminated union. But Prisma's model stores it as a plain string enum. Where does the conversion happen? How do you map from Prisma.Payment to your PaymentState type?
// Bonus — 20 Additional Marks
+8 marks — Webhook dispatcher: When a payment transitions to SUCCESS or FAILED, dispatch a webhook to the merchant's registered URL. Use a simple in-memory queue (or Bull/BullMQ with Redis) to retry failed webhooks up to 3 times with exponential backoff.
+7 marks — Payment expiry job: A cron job that finds PROCESSING payments older than 10 minutes and marks them FAILED with reason 'Payment timed out'. Reverse any wallet deductions made. Handle concurrency: use Prisma's update ... WHERE status = 'PROCESSING' to prevent double-processing.
+5 marks — API rate limiting per route: Different rate limits for different endpoints: POST /api/payments: 10/minute per user. POST /api/wallet/topup: 5/minute per user. POST /api/refunds: 3/minute per user. Use @fastify/rate-limit with Redis store.
