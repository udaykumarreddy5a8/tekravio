// The Problem
FinSmart Node.js uses Prisma's built-in Decimal type for all monetary fields and decimal.js for arithmetic. Never use JavaScript number for money. All balance modifications use Prisma interactive transactions (prisma.$transaction(async (tx) => {...})) to ensure atomicity. The Zod schema for the month parameter uses .transform() to convert the string '2026-06' to a Date object.
// 01 · Modules
Five Modules — 100 Marks

TypeScript strict mode throughout. No any. Every Zod schema exported from a schemas/ folder. Every Prisma query wrapped in a typed service class.

01
Account & Transaction Management
// 22 marks
▼

Typed account and transaction services with atomic balance updates.

Prisma Decimal: All monetary fields use Prisma's Decimal type: balance Decimal @default(0) @db.Decimal(19, 4). In TypeScript, use import Decimal from 'decimal.js' for all arithmetic. Never use number type for money.
Transaction service: createTransaction(dto: CreateTransactionDto): Promise<TransactionDto> uses a Prisma interactive transaction: prisma.$transaction(async (tx) => { /* deduct/credit balance + create transaction record */ }). The balance update uses a raw increment: tx.account.update({ where: { id }, data: { balance: { increment: amount } } }).
Account ownership: Every repository method that fetches or modifies an account must accept userId and include it in the where clause. Create a verifyAccountOwnership(accountId: string, userId: string): Promise<Account> utility that throws if ownership fails.
Balance recalculation: Implement recalculateBalance(accountId: string): Promise<Decimal> using Prisma's aggregate: prisma.transaction.aggregate({ where: { accountId, type: 'INCOME' }, _sum: { amount: true } }). Subtract expenses. Use this in tests to verify balance integrity.
02
Budget Management
// 20 marks
▼

Budget upsert and spending calculation with Prisma aggregations.

Budget upsert: Use Prisma upsert: prisma.budget.upsert({ where: { userId_category_month: { userId, category, month } }, create: {...}, update: { limitAmount } }). The compound unique index makes the upsert safe.
Budget with usage: getBudgetsWithUsage(userId, month): Promise<BudgetWithUsage[]>. One Prisma query using include + raw spend sum. Type the return: type BudgetWithUsage = Budget & { spentAmount: Decimal; usagePercentage: number; status: BudgetStatus }.
Zod for month parameter: Validate month query param as z.string().regex(/^\d{4}-\d{2}$/).transform(s => new Date(s + '-01')). The transform converts '2026-06' to a Date object automatically.
Budget summary: Return an array including categories with spending but no budget: use a Prisma findMany on transactions grouped by category, then merge with budget data in TypeScript.
03
Savings Goals & Deposits
// 20 marks
▼

Goal deposits with balance deduction and projected date calculation.

Goal deposit transaction: depositToGoal(userId, goalId, { accountId, amount, note }) uses a Prisma interactive transaction: deduct from account balance, create GoalDeposit, increment goal.currentAmount, check if goal is now achieved and update status. All in one atomic operation.
Projected date: Use decimal.js for all calculations. Average daily deposit rate from last 30 days using Prisma aggregate. const daysNeeded = remaining.div(dailyRate).ceil().toNumber(). Return null if no recent deposits.
Goal types: TypeScript: type GoalStatus = 'ACTIVE' | 'ACHIEVED' | 'ABANDONED'. Use a union type, not enum. The service sets status to ACHIEVED when currentAmount.gte(targetAmount).
Abandon goal: abandonGoal(userId, goalId) validates the goal belongs to the user and status is ACTIVE. Sets status to ABANDONED. This is the only valid way to close a non-achieved goal.
04
Analytics & Recurring
// 20 marks
▼

Aggregate reports and scheduled recurring transaction processing.

Monthly report: Use Prisma's groupBy for category breakdown: prisma.transaction.groupBy({ by: ['category'], where: {...}, _sum: { amount: true }, _count: true, orderBy: { _sum: { amount: 'desc' } } }). Return typed: CategoryBreakdown[].
6-month trend: Build the 6-month income vs expense trend using a Prisma raw query or a loop of aggregates. Return as TrendPoint[] where type TrendPoint = { month: string; income: Decimal; expenses: Decimal; net: Decimal }.
Recurring transaction job: Use node-cron or Fastify's lifecycle hooks for a daily job. Process all active recurring transactions where nextDueDate <= today in a loop. Wrap each in prisma.$transaction(). Catch per-item errors with logger.error() and continue.
Job idempotency: Ensure the recurring job does not double-process transactions if it runs twice in the same day (e.g., server restart). Use a processedDate field on the RecurringTransaction record: skip if processedDate equals today.
05
Testing & Deployment
// 18 marks
▼

Jest unit tests with Prisma mocks and one containerised integration test.

Prisma mock setup: Use jest-mock-extended or manual mocks: jest.mock('../prisma', () => ({ prisma: { account: { findFirst: jest.fn(), update: jest.fn() }, transaction: { create: jest.fn() }, $transaction: jest.fn() } })). Reset mocks in beforeEach.
Unit tests: 6 tests for TransactionService: (a) INCOME increases balance, (b) EXPENSE decreases balance, (c) insufficient balance throws typed error, (d) account not owned by user throws 403, (e) Decimal arithmetic: 100.10 + 200.20 = 300.30 (not 300.3000000000001), (f) budget status is OVER_BUDGET when usage > 100%.
Integration test: @testcontainers/postgresql test: create account with balance 1000, create expense transaction of 500, assert balance = 500, assert WalletTransaction created, assert balance recalculation matches.

// 02 · Design Questions
Answer in README.md

Node.js-specific design patterns — these come up in every backend interview.

Q1
Prisma's interactive transaction prisma.$transaction(async (tx) => {...}) gives you a scoped transaction client. Why do you need to use tx.account.update() inside the transaction instead of the regular prisma.account.update()?
Q2
You use decimal.js for arithmetic. But Prisma returns Decimal objects (from the @prisma/client/runtime package), not decimal.js Decimal objects. They are different types. How do you convert between them safely?
Q3
Your recurring transaction job runs at 8 AM daily. If the server was down from 7 AM to 9 AM, the job runs at 9 AM. It processes all transactions with nextDueDate <= today, which is correct. But what if the server was down for 3 days? Does your implementation handle multi-day backlogs correctly?
Q4
The budget summary must include categories that have transactions but no budget. Prisma's ORM cannot do a RIGHT JOIN from the budgets table. How do you implement this? Do you use Prisma's raw SQL ($queryRaw), or do you merge two separate queries in TypeScript?
