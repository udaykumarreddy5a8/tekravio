// The Problem
PayFlow FastAPI uses SQLAlchemy's INSERT ... ON CONFLICT DO NOTHING for idempotency. The UPDATE ... WHERE balance >= amount pattern for wallet deduction is atomic at the database level — no need for application-level locking. Payment status is a Python StrEnum stored as a native PostgreSQL ENUM. FastAPI dependencies (Depends()) handle auth, DB session, and role checking.
// 01 · Modules
Five Modules — 100 Marks

Type hints on every function. Pydantic v2 models for all request/response schemas. async def for all route handlers and database queries. mypy --strict must pass.

01
Wallet Management
// 20 marks
▼

Auto-created wallet with async balance operations.

Auto-create wallet: Use a SQLAlchemy event listener: @event.listens_for(User, 'after_insert') def create_wallet(mapper, connection, target): connection.execute(insert(Wallet).values(user_id=target.id, balance=0)). Or create it in the user registration service. Document your choice.
Deduct function: async def deduct_wallet(user_id: UUID, amount: Decimal, db: AsyncSession) -> Wallet. Use SQLAlchemy's update with a WHERE clause: stmt = update(Wallet).where(Wallet.user_id == user_id, Wallet.balance >= amount).values(balance=Wallet.balance - amount).returning(Wallet). If no row updated, raise InsufficientBalanceError.
Top-up endpoint: Pydantic: class TopUpRequest(BaseModel): amount: Decimal = Field(gt=0, le=Decimal('100000'), decimal_places=2); method: PaymentMethod. Route adds to wallet balance in a transaction.
Cursor pagination: Return {'data': items, 'next_cursor': items[-1].id if len(items) == size else None}. Query: stmt.where(WalletTransaction.id < cursor).order_by(WalletTransaction.id.desc()).limit(size).
02
Payment Processing & Idempotency
// 25 marks
▼

Idempotency via ON CONFLICT and status tracking.

Idempotency header: FastAPI dependency: async def idempotency_key(x_idempotency_key: str = Header(alias='X-Idempotency-Key')) -> str: return x_idempotency_key. Inject with Depends(idempotency_key) on the payment creation route.
INSERT ON CONFLICT: stmt = insert(Payment).values(..., idempotency_key=key).on_conflict_do_nothing(index_elements=['user_id', 'idempotency_key']). After executing: if no rowcount, the payment already existed — fetch and return it. This avoids a SELECT before INSERT.
Payment status StrEnum: class PaymentStatus(StrEnum): INITIATED = 'INITIATED'; PROCESSING = 'PROCESSING'; SUCCESS = 'SUCCESS'; FAILED = 'FAILED'. SQLAlchemy: status: Mapped[PaymentStatus] = mapped_column(Enum(PaymentStatus), default=PaymentStatus.INITIATED).
Async payment flow: In an async context: async with db.begin(): payment.status = PaymentStatus.PROCESSING; wallet = await deduct_wallet(...); payment.status = PaymentStatus.SUCCESS. Except InsufficientBalanceError: set FAILED. All changes committed atomically by the async with db.begin().
03
Refund Management
// 22 marks
▼

Refund lifecycle with Pydantic validation and typed errors.

Refund validator: Pydantic v2 model validator: @model_validator(mode='after') def validate_refund_amount(self) -> 'RefundCreate': if self.amount > self.max_refundable: raise ValueError(f'Amount exceeds refundable: {self.max_refundable}'); return self. The max_refundable is computed and passed to the schema.
Eligibility check: async def check_refund_eligibility(payment_id: UUID, user_id: UUID, db: AsyncSession) -> Payment. Fetch payment, check status == SUCCESS, check age <= 7 days (datetime.utcnow() - payment.processed_at <= timedelta(days=7)), check no existing PENDING refund. Raise specific HTTPException for each violation.
Process refund: Admin endpoint. SQLAlchemy transaction: credit wallet, set refund status to PROCESSED, update payment's refunded_amount using update(Payment).values(refunded_amount=Payment.refunded_amount + refund.amount).
Refund type detection: def get_refund_type(payment: Payment, refund: Refund) -> RefundType: total_refunded = payment.refunded_amount + refund.amount; return RefundType.FULL if total_refunded == payment.amount else RefundType.PARTIAL.
04
Merchant & Settlement
// 18 marks
▼

Merchant role, payment verification, and settlement aggregation.

Role-based dependency: async def require_merchant(current_user: User = Depends(get_current_user)) -> User: if current_user.role != Role.MERCHANT: raise HTTPException(status_code=403, detail='Merchant access required'); return current_user.
Settlement aggregation: Use SQLAlchemy with date_trunc: select(func.date_trunc('day', Payment.processed_at).label('day'), func.count().label('count'), func.sum(Payment.amount).label('total')).where(Payment.merchant_id == merchant_id).group_by('day').order_by('day').
Payment verification: GET /api/merchant/payments/verify with order_id: str = Query(...). Return: VerificationResponse(verified=payment.status == 'SUCCESS', status=payment.status, amount=payment.amount if payment.status == 'SUCCESS' else None).
Suspended check: Middleware function: async def check_merchant_status(merchant_id: UUID, db: AsyncSession) -> None: merchant = await db.get(User, merchant_id); if merchant.status == 'SUSPENDED': raise HTTPException(422, 'Merchant suspended'). Call from payment creation service.
05
Testing & Error Handling
// 15 marks
▼

pytest async tests for idempotency and balance operations.

Test idempotency: Mock SQLAlchemy to return no inserted rows on the first call (simulating an existing payment). Assert the service calls a SELECT to fetch the existing payment and returns it unchanged.
Wallet deduct test: Use SQLite in-memory for unit tests (AsyncSession with aiosqlite). Test: (a) deduct 400 from 500 → balance 100, (b) deduct 600 from 500 → InsufficientBalanceError, (c) assert the update WHERE clause includes balance >= amount.
FastAPI test client: Use httpx.AsyncClient(app=app). Test the X-Idempotency-Key requirement: POST to /api/payments without the header → 422 response with 'field required' error for the header.
Global exception handlers: Register handlers for: InsufficientBalanceError → 422, RefundNotEligibleError → 422, DuplicateIdempotencyKeyError → 200 (return existing). All return {'detail': message, 'code': error_code}.
// 02 · Design Questions
Answer in README.md

Python/FastAPI-specific patterns.

Q1
The SQLAlchemy UPDATE ... WHERE balance >= amount pattern for wallet deduction is atomic at the database level. But what if your application uses multiple database replicas (one primary for writes, replicas for reads)? Could this pattern break?
Q2
Python's async with db.begin(): auto-commits on success and auto-rolls back on exception. But what if an exception occurs AFTER the transaction commits but BEFORE the HTTP response is sent (e.g., during response serialization)? Is this possible with FastAPI?
Q3
Pydantic v2's @model_validator(mode='after') receives the fully validated model instance. You use it to validate that refund amount ≤ max_refundable. But max_refundable is a database value that must be fetched first. How do you pass this database value into the Pydantic model for validation?
Q4
FastAPI's Depends() creates a dependency chain. If three different route handlers all depend on get_current_user which depends on get_db, how many database sessions are created? Does FastAPI reuse the same session across dependency calls within a single request?

+5 marks — Structured error responses: Create a custom ErrorResponse Pydantic model: class ErrorResponse(BaseModel): detail: str; code: str; timestamp: datetime; path: str. All exception handlers return this model. Use FastAPI's responses parameter to document error responses in OpenAPI.
