// System Context
An e-commerce platform processes 50,000+ orders per day across three services: Order Service, Inventory Service, and Payment Service. Each runs independently with its own PostgreSQL database. They coordinate exclusively through Kafka events — no direct REST calls between services.

You are building the full system from scratch. The Saga pattern (choreography-based) ensures that a failed payment automatically triggers a stock rollback and order cancellation — no data inconsistency, no manual intervention, no distributed monolith.

Docker Compose brings up the entire system. Kafka, Zookeeper, Redis, three PostgreSQL instances, three Spring Boot services. One command. Everything running locally within 3 minutes.

01
Microservice Infrastructure & Domain Modelling
// 15 marks · Foundation — evaluated first

Three independent Spring Boot 3 services, each with its own PostgreSQL database, its own Flyway migrations, and its own Docker container. No shared database. No shared domain classes in a common module that both services import — that's a distributed monolith.

Three services: order-service, payment-service, inventory-service — each a separate Maven module with its own application.yml and Dockerfile
Domain model (Order Service): Order entity with status machine — PENDING → CONFIRMED → CANCELLED. Status transitions enforced at domain level, not just DB level.
Flyway migrations in each service — version-controlled schema. No spring.jpa.hibernate.ddl-auto=create anywhere in the codebase.
Docker Compose — one docker-compose.yml boots Kafka, Zookeeper, 3× PostgreSQL, 3× Spring Boot services. docker-compose up must work cleanly.
Kafka topic setup — topics created programmatically via NewTopic beans with correct partition count and replication factor for local dev.
Order.java — status machine enforced at domain levelJAVA
public Order confirmPayment() {
    if (this.status != OrderStatus.PENDING)
        throw new IllegalStateException(
            "Cannot confirm order in state: " + this.status);
    this.status = OrderStatus.CONFIRMED;
    this.updatedAt = Instant.now();
    return this;
}

public Order cancel(String reason) {
    if (this.status == OrderStatus.CONFIRMED)
        throw new IllegalStateException("Cannot cancel confirmed order");
    this.status = OrderStatus.CANCELLED;
    this.cancellationReason = reason;
    return this;
}
02
Saga Pattern — Choreography-Based Distributed Transaction
// 25 marks · The hardest part — highest weight

This is the core of the assignment. A customer places an order. Three things must happen atomically across three independent services and databases: stock reserved, payment processed, order confirmed. If any step fails, everything rolls back correctly — no stuck orders, no double-charged payments, no phantom stock reservations.

Happy path flow: POST /orders → ORDER_CREATED published → Inventory reserves stock, publishes STOCK_RESERVED → Payment charges card, publishes PAYMENT_SUCCESS → Order confirmed. Order status at each step must be visible via GET /orders/{id}.
Failure path — payment fails: PAYMENT_FAILED published → Inventory consumes it, releases the stock reservation → Order Service consumes it, cancels the order. No stuck data anywhere.
Failure path — stock unavailable: STOCK_RESERVATION_FAILED published → Order Service cancels order immediately. Payment is never attempted. No charge on the customer.
Event schema versioning: All Kafka events serialised as JSON with a eventVersion field. Consumers must handle both v1 and v2 schemas without breaking.
Saga state persistence: Order Service tracks the saga state in a saga_log table — which events have been received for each order. Allows replay on restart.
At-least-once delivery handled: Each consumer is idempotent. Processing the same event twice must produce the same result, not a duplicate transaction.

// Common Failure Mode

Most candidates implement the happy path correctly but break on the compensation path. We will deliberately test with a payment service that fails 30% of the time. Every failed payment must leave the system in a clean state. We will check the database directly.

03
Idempotency, Deduplication & Dead Letter Queue
// 20 marks · Production reliability

Kafka delivers messages at-least-once. Your network will retry. Your consumer will crash mid-processing. Every one of these scenarios must be handled correctly — not optimistically assumed to not happen.

Idempotency keys on payment: Each payment attempt has a UUID idempotency key stored in Redis with a 24h TTL. Reprocessing the same PAYMENT event returns the cached result without charging twice.
Outbox pattern on Order Service: Events are first written to an outbox table in the same transaction as the order write. A background scheduler publishes outbox events to Kafka and marks them sent. Zero event loss on service crash.
Consumer offset management: Manual offset commit ONLY after successful processing. A failed processing attempt must NOT commit the offset — the message must be reprocessed.
Dead Letter Queue (DLQ): After 3 failed processing attempts, the message is moved to a .DLQ topic. A monitoring endpoint exposes DLQ message count. DLQ messages can be replayed via an admin API.
Exactly-once processing test: Write a test that publishes the same Kafka event 5 times to the payment service. Verify that exactly 1 payment record exists in the database after all 5 are consumed.
04
Resilience4j — Circuit Breakers & Fault Tolerance
// 15 marks · Fault tolerance

Your Payment Service calls a mock external payment gateway. That gateway will be unreliable — slow responses, intermittent 500s, complete outages. Your service must degrade gracefully without cascading failure.

Circuit Breaker on payment gateway calls: Opens after 50% failure rate over 10 calls. In OPEN state, fail-fast with PAYMENT_FAILED event (no hanging threads). Half-open after 30 seconds.
Retry with exponential backoff: 3 attempts, 500ms initial delay, 2× multiplier. Retry only on transient errors (5xx, timeout) — never on 4xx client errors.
Bulkhead: Maximum 10 concurrent calls to the payment gateway. Requests beyond the limit are rejected immediately rather than queuing indefinitely.
TimeLimiter: Payment gateway calls timeout after 3 seconds. Timeout counts as a failure for circuit breaker purposes.
Metrics endpoint: Expose circuit breaker state, failure rate, call counts via Spring Boot Actuator at /actuator/circuitbreakers.
05
Redis Caching, Rate Limiting & Performance
// 15 marks · Production performance

The order status endpoint is called by the frontend every 2 seconds for live order tracking. At 10,000 concurrent orders, that's 20,000 DB queries/second. Redis eliminates this. Rate limiting prevents the API from being hammered in a different way.

Order status cache: Cache GET /orders/{id} response in Redis with 30s TTL. Cache must be invalidated immediately when order status changes (not wait for TTL expiry).
Inventory cache: Stock levels cached in Redis. Cache-aside pattern — read from cache, fall back to DB on miss, write to cache on DB read. Invalidate on every stock update.
Rate limiting per client IP: 100 requests/minute per IP on the order creation endpoint. Use Redis sliding window counter. Respond with HTTP 429 and Retry-After header on breach.
Distributed lock on stock reservation: Use Redis SETNX lock to prevent race condition when two orders try to reserve the last unit of stock simultaneously.
Cache warming: On service startup, pre-populate Redis with the 100 most recently updated order statuses. Justify why 100 in your README.
06
Test Suite — Integration, Contract & Load
// 10 marks · Quality discipline

A distributed system without tests is a distributed system nobody can change safely. We will run your tests. They must pass. They must test the right things.

Saga integration tests: Full happy path + both compensation paths tested end-to-end using EmbeddedKafka and TestContainers PostgreSQL. No mocking of Kafka — real broker.
Idempotency test: Publish same event 5 times, assert exactly 1 DB record created.
Circuit breaker test: Mock payment gateway to fail 6/10 requests. Assert circuit opens. Assert PAYMENT_FAILED event is published without calling the gateway while circuit is open.
Race condition test: Two concurrent requests for the last unit of stock. Assert exactly one succeeds, one gets STOCK_RESERVATION_FAILED. No negative stock allowed.
Load test (k6 or JMeter): 500 concurrent order creations. Assert zero saga inconsistencies in DB after all events are processed. Every order must be in a terminal state (CONFIRMED or CANCELLED).
