// The Problem
EduTrack Node.js API uses Fastify (not Express) for its built-in TypeScript support and performance. Zod for all request validation — define schemas in a schemas/ folder and infer TypeScript types from them with z.infer<>. Prisma 5.x for all database access — never use raw SQL for business logic. tsc --noEmit must pass with zero errors before submission.
// 01 · Modules
Five Modules — 100 Marks

TypeScript strict mode throughout. No any. Every Zod schema exported from a schemas/ folder. Every Prisma query wrapped in a typed service class.

01
Course & Content Management
// 20 marks
▼

Typed course CRUD with Zod validation and Prisma relations.

course.schema.tsZod + TypeScript
import { z } from 'zod';

export const CreateCourseSchema = z.object({
  title: z.string().min(5).max(100),
  category: z.enum(['PROGRAMMING', 'DESIGN', 'DATA_SCIENCE', 'BUSINESS', 'OTHER']),
  difficulty: z.enum(['BEGINNER', 'INTERMEDIATE', 'ADVANCED']),
  price: z.number().nonnegative().max(99999.99),
});

export type CreateCourseDto = z.infer<typeof CreateCourseSchema>;

// Reuse schema for update (all fields optional)
export const UpdateCourseSchema = CreateCourseSchema.partial();
Prisma schema: Define Course, CourseModule, Lesson models. Use @@unique for course slug (auto-generated from title). Use @default(autoincrement()) for moduleOrder so ordering works without manual index management.
Zod schemas: Create CreateCourseSchema, CreateModuleSchema, CreateLessonSchema with strict validation. Compose them: CourseWithModulesSchema = CreateCourseSchema.extend({ modules: CreateModuleSchema.array().min(1) }). Export all schemas from a single schemas/course.schema.ts.
Service layer: CourseService class with methods: create(dto: CreateCourseDto): Promise<CourseDto>. Use Prisma transactions to create course + modules + lessons atomically. Return a typed CourseDto using Prisma's Prisma.CourseGetPayload<typeof courseSelect>.
Publish validation: publishCourse(id: string): Promise<void> — validate at least 1 module with 1 lesson via Prisma count query. Throw a typed AppError class (extends Error) with a statusCode field.
02
Enrollment & Progress
// 22 marks
▼

Enrollment with business rules and progress calculation using Prisma aggregates.

Enrollment service: EnrollmentService.enroll(userId, courseId) — check: course is published, not already enrolled. Use prisma.enrollment.create() with a try/catch on Prisma's P2002 (unique constraint) error to handle duplicates cleanly.
Lesson completion: markLessonComplete(userId, lessonId): Promise<ProgressDto> — validate enrollment via Prisma: check that the lesson's course matches an enrollment for this user. Use an upsert for idempotency.
Progress query: Calculate progress in one Prisma query: prisma.$transaction([prisma.lesson.count({ where: { module: { courseId } } }), prisma.lessonProgress.count({ where: { userId, lesson: { module: { courseId } } } })]). Return both counts and compute percentage.
Completion status: getCompletionStatus(userId, enrollmentId): Promise<CompletionStatusDto>. Typed return: { lessonsComplete: boolean; quizzesPassed: boolean; eligible: boolean; certificateCode: string | null }.
// Note

For the completion certificate code, generate it with crypto.randomUUID() from Node's built-in node:crypto module. Store it on the Enrollment record. Never regenerate it once set.

03
Quiz System
// 22 marks
▼

Quiz creation, attempt submission, and scoring with TypeScript type safety.

Quiz attempt types: Define the attempt result type: type AttemptResult = { score: number; status: 'PASSED' | 'FAILED'; correctCount: number; totalCount: number }. The service method signature: submitAttempt(userId: string, quizId: string, answers: AnswerDto[]): Promise<AttemptResult>.
Scoring logic: In the service: map answers to a Map<string, string> (questionId → selectedOptionId). Then for each question in the quiz, check if the selected option's isCorrect is true. Use Prisma's include: { questions: { include: { options: true } } }.
Attempt validation: Before scoring: fetch all attempts for this user+quiz. If status PASSED exists: throw new AppError('Quiz already passed', 409). If count >= maxAttempts: throw new AppError('Max attempts exceeded', 422). Use TypeScript's discriminated union for error types.
GET quiz for student: GET /api/quizzes/:id — return quiz with questions and options BUT filter out the isCorrect field using a Prisma select that explicitly omits it. Never expose which option is correct before submission.
04
Search & Dashboards
// 18 marks
▼

Typed search with Prisma where clauses and efficient aggregation queries.

Course search: Build searchCourses(filters: CourseFiltersDto) using a dynamic Prisma where object. TypeScript: const where: Prisma.CourseWhereInput = { published: true }. Conditionally add category, difficulty, price range. Use Prisma's _count to include enrollment count.
Student dashboard: Return type: interface StudentDashboard { enrollments: EnrollmentWithProgress[]; completedCourses: CompletedCourse[]; }. Fetch all data in one Prisma transaction.
Instructor dashboard: InstructorDashboard.perCourse includes completionRate: number. Calculate with two Prisma aggregate queries: total enrolled, students with all lessons done.
Pagination helper: Create a reusable paginate<T>(model, args, page, size): Promise<PaginatedResponse<T>> generic function that returns { data, total, page, size, totalPages }.
05
Testing & Error Handling
// 18 marks
▼

Fastify error handling, Jest unit tests, and one Testcontainers integration test.

AppError class: class AppError extends Error { constructor(public message: string, public statusCode: number, public code?: string) { super(message) } }. Register a Fastify setErrorHandler that catches AppError (returns statusCode + message) and Zod errors (returns 400 + formatted field errors).
Unit tests: Jest tests for QuizAttemptService: mock Prisma with jest.mock('../prisma'). Test: (a) successful pass returns PASSED status, (b) already-passed quiz throws 409, (c) max attempts exceeded throws 422, (d) score calculation: 3 of 5 correct = 60.
Integration test: One @testcontainers/postgresql integration test: seed a course, enroll a student, mark all lessons complete, verify completion status returns eligible=true. Use Fastify's inject method for HTTP requests.
Structured logging: Use pino (built into Fastify). Every service method logs: logger.info({ userId, courseId }, 'Student enrolled in course'). Errors logged with logger.error({ err, userId }, 'Enrollment failed'). Log level configurable via LOG_LEVEL env var.
// 02 · Design Questions
Answer in README.md

Node.js-specific design patterns — these come up in every backend interview.

Q1
Prisma's findUnique throws an error if the record doesn't exist when you use the orThrow variant. But if you use findUnique (without orThrow), it returns null. Which do you use in your service methods, and how do you handle the null case with TypeScript's type narrowing?
Q2
You have a service method that does: (1) check enrollment exists, (2) mark lesson complete, (3) check if course is now complete, (4) generate certificate if eligible. Should this be one Prisma transaction? What happens if step 3 or 4 fails after step 2 succeeds?
Q3
Fastify uses JSON schema for request validation by default, but you're using Zod. How do you wire up Zod validation to Fastify's request parsing? Do you use the fastify-type-provider-zod plugin or validate manually in the route handler? What's the difference?
Q4
Your pagination function takes a generic T: paginate<T>(). But Prisma's model types are not directly generic — you need to call prisma.course.findMany() or prisma.user.findMany(). How do you write a type-safe paginate function that works for any Prisma model?
