01
Async Document Ingestion Pipeline
// 15 marks · Pipeline foundation

Document upload must be non-blocking. The API accepts the file, stores it in S3, creates a DB record, and returns immediately with a job ID. All processing happens asynchronously in Celery workers. The client polls or subscribes via WebSocket for status updates.

FastAPI upload endpoint: Accepts PDF/DOCX/PNG/JPG, validates MIME type and size (max 50MB), stores to S3 with documents/{org_id}/{uuid}/{filename} key, creates Document record with status QUEUED.
Celery chord pipeline: ocr_task → llm_extract_task → embed_task chained. If any stage fails, subsequent stages don't run. Document status updated at each stage: PROCESSING_OCR → PROCESSING_EXTRACT → PROCESSING_EMBED → READY.
Server-Sent Events (SSE): GET /documents/{id}/status streams document processing status updates in real-time. Client reconnects automatically on disconnect. Close stream when document reaches terminal state.
AWS Textract integration: For scanned PDFs (image-based), call Textract synchronous API for <10 pages, async API for larger documents. Poll for async completion. Merge page results into single text corpus.
Pre-signed upload URLs: Optionally, expose POST /documents/presigned-url so clients can upload directly to S3, bypassing your API server entirely. Trigger Celery task via S3 event notification.

@celery.task(bind=True, max_retries=3)
def process_document(self, document_id: str):
    # Build a chord: OCR → extract → embed in sequence
    pipeline = chain(
        ocr_task.s(document_id),
        llm_extract_task.s(),
        embed_task.s(),
    )
    result = pipeline.apply_async()
    return result.id

@celery.task(bind=True, max_retries=5, default_retry_delay=60)
def ocr_task(self, document_id: str) -> dict:
    try:
        text = extract_text_from_s3(document_id)
        update_document_status(document_id, "PROCESSING_EXTRACT", extracted_text=text)
        return {"document_id": document_id, "text": text}
    except TextractThrottling as exc:
        raise self.retry(exc=exc, countdown=2 ** self.request.retries)
02
LLM Extraction — Structured Output from Unstructured Documents
// 25 marks · The hardest part

Given raw text from a contract, extract structured data: parties, dates, monetary values, clause types, governing law. The output must be a valid Pydantic model — not a free-form string. Handle hallucinations, parsing failures, and context window limits.

Document type classifier: First LLM call classifies the document (CONTRACT, INVOICE, REPORT, OTHER). Different extraction schemas for each type. Classifier confidence score stored with result.
Structured extraction with function calling: For CONTRACT type, extract: parties: List[str], effective_date: date, expiry_date: Optional[date], total_value: Optional[Decimal], currency: str, governing_law: str, penalty_clauses: List[PenaltyClause]. Pydantic validates the LLM response.
Context window chunking: Documents exceeding the model's context window are split into overlapping chunks (512-token overlap). Extract from each chunk. Merge results with conflict resolution (earliest date wins, largest value wins, union of parties).
Confidence scoring: Each extracted field gets a confidence score (0.0–1.0) based on how many chunks agreed on the value. Fields with confidence < 0.6 are flagged for human review. Store in extraction_results.confidence_scores (JSONB).
Hallucination detection: After extraction, verify dates and amounts are actually present in the source text (exact string match). Fields that are "hallucinated" (not in source text) are cleared and flagged. Log all hallucinations with document ID for model improvement.
Retry on parse failure: If the LLM returns invalid JSON or a schema violation, retry the call with a more explicit prompt that includes the validation error. Max 2 retries before marking extraction as FAILED.

03
Vector Embeddings & Semantic Search
// 20 marks · Search intelligence

Users don't search by keyword — they ask questions: "Which contracts expire in Q3 2026?" "Find all invoices from ACME Corp over £10,000." The search layer combines vector similarity (semantic) with structured filters (SQL) in a single query.

Embedding generation: Generate embeddings for each document chunk (max 512 tokens) using OpenAI text-embedding-3-small or equivalent. Store vectors in PostgreSQL pgvector column. Batch embed — don't call the API one chunk at a time.
Hybrid search query: Combine 1 - (embedding <=> query_vector) (cosine similarity) with ts_rank(tsv, query) (full-text rank) using a weighted sum. Configurable alpha parameter (0 = pure keyword, 1 = pure semantic).
Metadata filter pushdown: Search supports filter parameters: document_type, date_from, date_to, min_value, max_value, parties__contains. Filters applied as SQL WHERE clauses before vector search — not post-filter.
HNSW index: Create HNSW index on the embedding column (vector_cosine_ops). Demonstrate query time with and without index on 10,000 documents. Document the difference in your README.
Re-ranking: After ANN search returns top-20 candidates, re-rank using cross-encoder model (or second LLM call). Return top-5 with relevance explanation generated by LLM.
04
Celery Worker Architecture — Concurrency, Priority & Monitoring
// 15 marks · Worker reliability

Three worker types with different resource profiles: OCR workers are I/O bound, LLM workers are network bound and expensive, embedding workers are CPU bound. They need different concurrency settings, separate queues, and independent scaling.

Three worker pools: ocr-worker (concurrency: 10, prefetch: 4), llm-worker (concurrency: 3, rate_limit: 10/min to respect API limits), embed-worker (concurrency: 8). Each defined in Docker Compose as a separate service.
Task routing: OCR tasks → ocr_queue, LLM tasks → llm_queue, embed tasks → embed_queue. Priority queue for llm_queue — paid tier documents processed before free tier.
Result backend: Task results stored in Redis with 24h TTL. GET /documents/{id}/extraction reads from Redis cache before hitting DB.
Flower monitoring: Mount Flower (Celery monitoring) at /admin/workers. Show active tasks, worker status, task history, failure rate per queue. We will check this during review.
Dead letter handling: Failed tasks after max retries moved to dlq queue. Admin endpoint to list DLQ tasks, inspect payloads, and replay individual tasks.
05
API Design, Streaming & Performance
// 15 marks · Production API quality

FastAPI is async-first. Every DB call, every S3 call, every Celery dispatch must use async properly. Synchronous blocking calls inside async endpoints are a common mistake that serialises all requests through a single thread.

Fully async SQLAlchemy: Use asyncpg driver and AsyncSession. Zero session.execute() calls in sync context inside async endpoints. Demonstrate with a load test that 100 concurrent requests complete in < 2 seconds.
Streaming search results: GET /search?stream=true returns results via SSE as they're found — first results appear before the full query completes. Frontend can render progressively without waiting for all 20 results.
Pagination with cursor: All list endpoints use cursor-based pagination (not offset). Cursor is an opaque base64-encoded value. Stable ordering — adding new documents doesn't shift pages.
Response caching: Search results cached in Redis with 60s TTL keyed by query hash + filters. Cache invalidated when new documents of matching type are indexed.
Background task cancellation: DELETE /documents/{id}/processing cancels in-progress Celery tasks for a document. Celery worker handles TaskRevokedError gracefully — no partial state left in DB.

// Q1
Your LLM extraction Celery task runs for 4 minutes and is killed by a container OOM event midway through a 200-page contract. When it's retried, it starts from scratch. How do you implement checkpointing so retries resume from the last successful page?
// Q2
OpenAI's API starts returning 429 rate limit errors during peak usage. Your LLM worker queue is growing. You can't just retry immediately — that makes it worse. Design a back-pressure mechanism that slows ingest during API rate limiting without dropping documents.
// Q3
A 500-page PDF is uploaded. Your chunking strategy splits it into 200 chunks of ~512 tokens each. That's 200 embedding API calls and 200 vector rows in PostgreSQL. At 10,000 documents per day, this becomes a storage and query performance problem. How do you approach this trade-off?
// Q4
You discover that your LLM extraction is fabricating penalty clause amounts that don't exist in the source text (hallucinating) on roughly 8% of contracts. Your current hallucination detection catches 60% of these. What additional detection techniques would you implement, and what is the acceptable threshold for a production contract management system?
// Q5

A customer complains that a contract they found on Monday can't be found on Friday. Walk through all the reasons this can happen and how you would debug it systematically.
