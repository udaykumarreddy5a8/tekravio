// The Problem
ConnectHub is a social platform. Users have profiles with a public or private visibility setting. Anyone can view a public account's posts. A private account's posts are visible only to approved followers. Sending a follow request to a private account creates a PENDING request; only when the account owner approves does the requester become a follower.

The home feed shows posts from all accounts the user is APPROVED-following, sorted newest first. This is a real-world query challenge: efficient pagination over a join of posts + follow relationships without loading everything into memory.

01
User Profiles & Authentication
// 20 marks
▼

Registration, login, and profile management with JWT.

User entity: Fields: username (unique, 3–30 chars, alphanumeric+underscore), email (unique), passwordHash, displayName, bio (max 150 chars), avatarUrl, isPrivate (default false), isActive, createdAt. Expose a DTO without passwordHash in responses.
Registration & Login: POST /api/auth/register — validate username and email uniqueness, hash password with BCrypt, create user. POST /api/auth/login — validate credentials, return JWT (valid 24h). POST /api/auth/refresh — accept a refresh token, return a new JWT (optional for bonus).
Profile management: GET /api/users/{username} — public profile: if private and viewer is not an approved follower, return limited view (username, displayName, avatarUrl, followerCount, followingCount, postCount — but NOT posts). PUT /api/users/me — update own profile: displayName, bio, avatarUrl, isPrivate. GET /api/users/me — own full profile.
Search: GET /api/users/search?q=john&page=0&size=10 — search by username or displayName (case-insensitive, partial match). Return basic profile info. Exclude suspended/inactive users.
// Note

Keep the JWT implementation simple. Use io.jsonwebtoken:jjwt. A single filter class that validates the token and sets the SecurityContext is sufficient. Don't overcomplicate the security config.

02
Follow System & Connections
// 22 marks
▼

The follow system handles both public (instant) and private (request-based) accounts.

FollowService.java — follow logicService
@Transactional
public FollowResponse follow(String targetUsername) {
    User target = userRepository.findByUsername(targetUsername)
        .orElseThrow(() -> new UserNotFoundException(targetUsername));
    User me = currentUser();

    if (me.getId().equals(target.getId()))
        throw new CannotFollowSelfException();

    followRepository.findByFollowerAndFollowing(me, target).ifPresent(f -> {
        if (f.getStatus() == FollowStatus.APPROVED)
            throw new AlreadyFollowingException();
        if (f.getStatus() == FollowStatus.PENDING)
            throw new FollowRequestAlreadySentException();
        if (f.getStatus() == FollowStatus.BLOCKED)
            throw new UserBlockedException();
    });

    FollowStatus status = target.isPrivate()
        ? FollowStatus.PENDING : FollowStatus.APPROVED;
    return followMapper.toResponse(followRepository.save(
        Follow.builder().follower(me).following(target).status(status).build()));
}
Follow entity: Fields: followerId (User), followingId (User), status (PENDING, APPROVED, BLOCKED), createdAt, updatedAt. A user cannot follow themselves. @UniqueConstraint(columnNames = {"follower_id", "following_id"}).
Follow / Unfollow: POST /api/follow/{username} — follow a user. If target account is public: create Follow with status APPROVED immediately. If private: create Follow with status PENDING. If already following (APPROVED) or has pending request: return appropriate conflict (already following / request already sent). DELETE /api/follow/{username} — unfollow (delete the Follow record).
Follow request management (private accounts): GET /api/follow/requests — list incoming PENDING requests for the authenticated user. PUT /api/follow/requests/{requestId}/approve — set status APPROVED. PUT /api/follow/requests/{requestId}/reject — delete the request. These are only valid for private account owners.
Block: POST /api/block/{username} — block a user. Creates or updates a Follow record with status BLOCKED. A blocked user cannot see the blocker's posts, cannot follow the blocker, and cannot see the blocker's profile. If the blocked user was already following, that follow is removed. DELETE /api/block/{username} — unblock.
Follow stats: GET /api/users/{username}/followers?page=&size= and /following — paginated list. For private accounts, only the account owner can see their follower/following lists. Return followerCount and followingCount on all profile responses.
03
Posts & Visibility Rules
// 22 marks
▼

Posts with text and image URLs, visibility controlled by account type and follow status.

Post entity: Fields: author (User), content (text, max 2000 chars), imageUrls (stored as list/array, max 5), visibility (PUBLIC, FOLLOWERS_ONLY, PRIVATE), likeCount (denormalised int, updated on like/unlike), commentCount (denormalised int), isDeleted (soft delete), createdAt, updatedAt. Index on (author, createdAt DESC).
Create / Edit / Delete: POST /api/posts — authenticated users only. PUT /api/posts/{id} — edit own posts (content and imageUrls only). DELETE /api/posts/{id} — soft delete (set isDeleted=true). Soft-deleted posts return 404 on direct access, and are excluded from feeds.
Post visibility logic: GET /api/posts/{id} — enforce: (a) PRIVATE posts: only the author can see. (b) FOLLOWERS_ONLY posts on a private account: only APPROVED followers can see. (c) All posts on a public account with FOLLOWERS_ONLY or PUBLIC visibility: accessible to all authenticated users. Return 403 with a clear message (not 404) when access is denied.
User's post list: GET /api/users/{username}/posts?page=0&size=10 — sorted newest first. Apply visibility rules: if viewer is not an approved follower of a private account, return 403. For public accounts, return all non-private, non-deleted posts.
// Note

Denormalise likeCount and commentCount on the Post entity for performance — increment/decrement them on like/unlike/comment. This means the count is always available without a join.

04
Feed, Likes & Comments
// 20 marks
▼

Home feed, engagement features, and the comment thread.

Feed JPQL queryRepository
@Query("SELECT p FROM Post p " +
       "WHERE p.author.id IN " +
       "    (SELECT f.following.id FROM Follow f " +
       "     WHERE f.follower.id = :userId " +
       "     AND f.status = 'APPROVED') " +
       "AND p.isDeleted = false " +
       "AND p.visibility != 'PRIVATE' " +
       "ORDER BY p.createdAt DESC")
Page<Post> findFeedForUser(
    @Param("userId") UUID userId,
    Pageable pageable
);
Home feed: GET /api/feed?page=0&size=20 — posts from users the authenticated user APPROVED-follows, excluding soft-deleted, newest first. Build this with a JPQL query joining Post and Follow: SELECT p FROM Post p WHERE p.author IN (SELECT f.following FROM Follow f WHERE f.follower = :me AND f.status = 'APPROVED') AND p.isDeleted = false ORDER BY p.createdAt DESC. Paginate with Spring's Pageable.
Likes: POST /api/posts/{id}/like — like a post. Validate: cannot like own post, cannot like twice (if already liked, throw AlreadyLikedException). On success, increment post.likeCount atomically. DELETE /api/posts/{id}/like — unlike (decrement likeCount). GET /api/posts/{id}/likes?page=&size= — list of users who liked (basic profile only). Apply post visibility rules here too.
Comments: POST /api/posts/{id}/comments — add comment. Fields: content (max 500 chars), parentCommentId (null for top-level, UUID for reply). Support only 1 level of nesting (replies to top-level comments only; you cannot reply to a reply). GET /api/posts/{id}/comments?page=&size= — top-level comments with their direct replies embedded (not paginated separately). DELETE /api/comments/{id} — author or post author can delete.
Comment count: When a comment is created, increment post.commentCount. When deleted, decrement. Use @Modifying @Query for atomic update, not fetching the post and setting the count.
05
Notifications & Testing
// 16 marks
▼

In-app notifications for social events and the tests that verify the access control logic.

Notification entity: Fields: recipientId, type (NEW_FOLLOWER, FOLLOW_REQUEST, FOLLOW_APPROVED, POST_LIKED, POST_COMMENTED), actorId (who triggered it), referenceId (postId or followId depending on type), message (pre-formatted text), isRead, createdAt. Notifications are created as side effects of follow/like/comment actions — no external queue needed for this assignment.
Notification triggers: On NEW_FOLLOWER (public account): notify the followed user. On FOLLOW_REQUEST: notify the account owner. On FOLLOW_APPROVED: notify the requester. On POST_LIKED: notify the post author (not if user likes own post). On POST_COMMENTED: notify the post author (not if author comments on own post).
Notification APIs: GET /api/notifications?read=false&page=0&size=20 — user's own notifications, newest first. PUT /api/notifications/{id}/read — mark one as read. PUT /api/notifications/read-all — mark all as read. GET /api/notifications/unread-count — returns {count: N} (called frequently by frontend).
Unit tests: Test the follow service: (a) following a public account → status APPROVED, (b) following a private account → status PENDING, (c) following self → CannotFollowSelfException, (d) duplicate follow → AlreadyFollowingException, (e) following a user who blocked you → UserBlockedException, (f) blocked user attempts to follow the blocker after being blocked → same exception. 6 tests.
// Note

Create notifications synchronously for now (in the same transaction). Note in your README where you would use an async mechanism (Spring Events or a message queue) in a production system to avoid coupling the main operation to notification delivery.

// 02 · Design Questions
Answer in README.md
Q1
User A follows User B (private). User B approves the follow request. Now User A can see User B's posts. User B later changes their account from private to public. Does User A's follow relationship change? What about User C who had a PENDING follow request at the time of the switch?
Q2
The home feed query does a JOIN between posts and follows tables. For a user who follows 500 people who each post 10 times per day, how many rows are potentially scanned in the feed query? What index on the Post table makes this query fast?
Q3
You soft-delete posts (isDeleted=true) instead of hard-deleting. What are the advantages of soft delete? What happens to likes and comments on a soft-deleted post? Should they also be soft-deleted? How does your system handle GET /api/posts/{id} for a soft-deleted post?
Q4
You store likeCount and commentCount on the Post entity to avoid slow COUNT queries. But now there's a risk: if two users like a post simultaneously, and both read likeCount=5, both increment to 6, you end up with 6 instead of 7. How do you fix this? Write the @Query that increments atomically.
