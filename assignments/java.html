// 01 · The Brief

What You're Building

Tekravio manages sprint-based consulting projects for enterprise clients. Every project has tasks, deadlines, and engineers assigned. Your job is to build the backend REST API that powers this system.

This is not a todo app. This is a Project & Sprint Tracker — the kind of system that runs real consulting operations. Think about what breaks in production. Think about what an enterprise CTO would reject in a code review. Build accordingly.

// The System You're Building

A Spring Boot REST API for Tekravio's internal sprint tracker. Clients have projects. Projects have sprints. Sprints have tasks. Engineers are assigned to tasks. Everything is tracked, filtered, and reported through your API.

02
REST API — CRUD Endpoints
// 25 marks · Core Delivery

Build clean, RESTful endpoints for all entities. Use proper HTTP methods, status codes, and response structures. An enterprise client's frontend team will consume these.

MethodEndpointDescription
POST/api/clientsCreate a new client
GET/api/clientsList all clients (with pagination)
GET/api/clients/{id}Get client by ID
PUT/api/clients/{id}Update client details
DELETE/api/clients/{id}Soft delete a client
POST/api/projectsCreate project for a client
GET/api/projects/{id}/sprintsGet all sprints for a project
POST/api/sprints/{id}/tasksAdd task to sprint
PUT/api/tasks/{id}/statusUpdate task status
PUT/api/tasks/{id}/assign/{engineerId}Assign engineer to task
✓
Use DTOs for all request and response bodies — never expose JPA entities directly
✓
Correct HTTP status codes — 201 for create, 404 for not found, 400 for bad input
✓
Consistent JSON response wrapper: {"success": true, "data": {}, "message": ""}
✓
Pagination on all list endpoints — page, size, sort params
03
Validation & Exception Handling
// 20 marks · Production Readiness

A real API never crashes with a 500. Handle every edge case. A frontend developer should never get a raw stack trace from your API.

✓
Bean validation on all request DTOs — @NotNull, @NotBlank, @Email, @Size etc.
✓
Global exception handler using @ControllerAdvice
✓
Custom exceptions: ResourceNotFoundException, InvalidStatusTransitionException, EngineerNotAvailableException
✓
Business rule: An engineer marked isAvailable=false cannot be assigned to a task
✓
Business rule: A task's status can only move forward — TODO→IN_PROGRESS→REVIEW→DONE. Reject backwards transitions.
✓
Meaningful error responses with field-level validation messages
Expected error response shapeJSON
{
  "success": false,
  "message": "Validation failed",
  "errors": [
    { "field": "email", "message": "must be a valid email" },
    { "field": "name",  "message": "must not be blank" }
  ],
  "timestamp": "2026-05-30T10:30:00"
}
04
Business Logic — Sprint Intelligence
// 25 marks · Think Like an Engineer

This is where average submissions fall apart. Anyone can do CRUD. Build the logic that makes the system useful.

✓
Sprint Summary API — GET /api/sprints/{id}/summary → returns: total tasks, completed %, average completion time, tasks by priority, overdue tasks count
✓
Engineer Workload API — GET /api/engineers/{id}/workload → returns: active tasks count, tasks by status, total estimated vs actual hours
✓
Project Health API — GET /api/projects/{id}/health → returns a simple health score (0–100) based on sprint completion rate and overdue tasks. Define your own formula and explain it in the README.
✓
Available Engineers API — GET /api/engineers/available?stack=JAVA → returns engineers by stack who are available and have fewer than 3 active tasks
✓
Filtering — GET /api/tasks?status=IN_PROGRESS&priority=HIGH&sprintId=1 → multi-param filtering using Spring Data JPA Specifications or dynamic queries
// Uday's Note

The Project Health API has no right answer. We want to see how you think, not what formula you picked. Define it. Justify it. Own it. That matters more than the number you return.

05
Testing
// 15 marks · You Don't Skip Tests

We don't ship untested code. Not even interns. Write tests that prove your code works — and prove it breaks correctly too.

✓
Unit tests for all service layer methods using JUnit 5 + Mockito
✓
Integration tests for at least 3 controller endpoints using @SpringBootTest + MockMvc
✓
Test the sad paths — what happens when you assign an unavailable engineer? When status goes backwards?
✓
Minimum coverage: 60% on service layer (use JaCoCo — include the report)
TaskServiceTest.java — example structureJAVA
@ExtendWith(MockitoExtension.class)
class TaskServiceTest {

    @Mock private TaskRepository taskRepository;
    @Mock private EngineerRepository engineerRepository;
    @InjectMocks private TaskService taskService;

    @Test
    void assignTask_whenEngineerUnavailable_throwsException() {
        // Arrange
        Engineer eng = new Engineer();
        eng.setAvailable(false);
        when(engineerRepository.findById(1L)).thenReturn(Optional.of(eng));

        // Act + Assert
        assertThrows(EngineerNotAvailableException.class,
            () -> taskService.assignEngineer(1L, 1L));
    }
}
